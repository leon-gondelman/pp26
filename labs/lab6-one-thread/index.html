Part 1: Correctness and coordinationon paper

Three questions on the introduction. We write the answers on a page of our own.

From the lecture

Safety: nothing bad ever happens; a violation happens at one definite moment. Liveness: something good eventually happens; no finite beginning of an execution violates it: however long the execution has run, the good thing can still happen later.

Coordination: when a process may act depends on what the others have done or are doing. It has two forms: not before (P waits until Q has acted) and not at the same time (P and Q are never both inside the part that changes the shared data).

Linearizability: in every execution, the calls can be put in one sequence such that each call answers as it would if the calls were made alone, one after the other, in that order; and a call that returned before another was made comes first in the sequence.

Part 2: Asynchronous functions in JavaScriptpredict on paper, then run

We read each program, choose one of the three answers, and write it down. Then we run the program in warmup/js/, for example node q4_two_loads.mjs. Where the run differs from our answer, we find the property that explains it. In question 9 we write a function, then run it.

From the lecture

Property 1 · Suspension. An asynchronous function is suspended only at an await written in it. A caller that does not await the call goes on.

Property 2 · Waiting is not running. Waits overlap. On one thread, our own code does not: at any moment at most one computation is running.

Property 3 · Run-to-completion. The loop takes the next function from the queue only when the stack is empty: the running code has returned, and so has everything it called. Nobody takes the thread away from running code.

Property 4 · Atomicity between suspension points. A stretch of a function's text with no await in it is atomic with respect to all other code of ours: nobody observes it half done. A function called inside the stretch runs at once, inside its caller, and is part of the stretch.

In JavaScript, in addition, a call runs the function up to its first await and then returns a promise; and every await is a suspension point, even await null.

From the appendix

Continuation: the continuation of a point in a computation is the rest of the computation from that point, as a function of the value expected there. In double(x) + 1, while double(x) is computed, the rest is v => v + 1.

Continuation-passing style: a function whose result is not there when it is called takes its continuation k as an argument, and calls k when the result exists.

Generator: g = gen() makes a generator and runs nothing. g.next(v) runs it up to its next yield, or to its end; v becomes the value of the yield at which g was suspended (on the first call there is none, and v is dropped). It returns an object { value, done }: the value yielded, and whether the generator has finished.

Limits and further reading

What ours.mjs leaves out: then returns nothing, so continuations cannot be chained; there is no second continuation, for failure, as JavaScript's then(onFulfilled, onRejected) has; and the loop is started with a timer of the host, so it runs on top of JavaScript's own loop.

Lab 5's Part C is the same idea in OCaml: a continuation kept and called later, and two continuations, k and h. Reading: Leroy, Control structures in programming languages (2026), chapters 6 and 7.
