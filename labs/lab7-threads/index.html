Threads: Four Structures and a Mini Ray Tracer

The lab has two halves. The warm-up is four Java classes to finish: a counter, a group of worker threads, a bounded buffer and a barrier. Each class is a file with holes, a contract that says what the class must do, and a check program that tests it. The quest is a mini ray tracer, made multi-threaded with those four classes.

Three properties recur. Mutual exclusion: no two threads are inside the code that changes shared data at the same time. Ordering: a thread acts only after another has acted. Visibility: a write on one thread is seen by a read on another. A lock, an atomic instruction and a copy per thread give mutual exclusion. A join, a barrier and a monitor's wait give ordering, and visibility with it. A volatile write gives visibility only.

Part 1: The counter, three waysat the keyboard

RacyCounter loses adds. The exercise writes the lecture's three repairs behind one interface. The lock is in block 1 of the lecture; the atomic and the count per thread are in block 2 (examples 6 and 8), so after block 1 alone, LockedCounter comes first.

From the lecture

n++ on a shared field is three steps, read, add, write, and another thread may run between any two of them (example 1; rule 3). The repairs: a lock, one thread at a time in the critical section (example 3); an atomic instruction that makes the three steps one (example 6); a count per thread, summed after the join (example 8).

The contract

add loses no add: once every adding thread has been joined, get() equals the number of adds. During the run, get() returns at least the adds completed before the call began and at most the adds begun before it returned. add takes the worker's index; only PerWorkerCounter uses it, and it also offers get(worker), one worker's own count. Its get() sums the slots one after another and is not a snapshot.

RacyCounter breaks both clauses: a read may never see a write, and a plain long may be read half-written.

Exercise 1

Given the interface Counter, RacyCounter, and the classes LockedCounter, AtomicCounter and PerWorkerCounter with their holes, write the three: LockedCounter with synchronized on both methods; AtomicCounter with an AtomicLong and incrementAndGet; PerWorkerCounter with an AtomicLongArray, one slot per worker, written only by its owner and summed by get(); of the array's methods, incrementAndGet(i), get(i) and length() suffice. The slots are atomic so that a read during the run sees the writes; a plain array would be correct only after the join. Before running each class, write a prediction in the comment above it: the exact total, less, more, or it depends on the run. Optional: a fourth counter on the lecture's spin lock, AtomicBoolean.getAndSet.

The check: java -cp out CounterCheck racy, then locked, atomic, perworker. The check has two halves. The first forces one lost update: two threads run the three steps of n++ with a barrier between the read and the write, so both read the same value; the output shows the two reads, the two writes and the lost add. The second runs twelve threads that add to the named counter while a reader calls get() repeatedly. After the join the total must equal the number of adds; every read during the run must lie within the contract's bounds and never decrease.

Part 2: Workers: start, join, stopat the keyboard

n threads running one indexed task, a join, and a stop flag.

From the lecture

new Thread(r) creates a thread, start() starts it, and join() waits for it to end and makes its writes visible to the joining thread (example 1). A flag read by another thread is volatile or atomic, never a plain field (rule 9).

The contract

new Workers(n), then start(task), runs task once on each of n threads, with the thread's index. A second start on the same object throws IllegalStateException; a restart uses a fresh Workers. join() returns when every thread has ended, and everything the threads wrote is visible after it. stop() makes stopped() return true on every worker from some point on. It ends no thread: a task that never calls stopped() never stops.

With the flag plain, "from some point on" does not hold: the language permits a worker never to see the write.

Exercise 2

Given the class Workers, with its threads kept in an array, write start, join and stop, and leave the flag plain, as declared. A lambda captures only an effectively final local variable, so start copies the loop index into a final local, final int id = i;, before new Thread(() -> task.accept(id)). A task reads the flag through the object:

The check: java -cp out WorkersCheck, three lines. First: each index runs once, on its own thread, and every slot the workers wrote is present after the join. Second: a second start throws IllegalStateException. Third: workers spin on an empty loop that tests only the flag; the check calls stop, waits until a deadline, and reports which workers stopped. The verdict comes from the flag's declaration, not from the run: a plain flag fails, because no rule requires a plain read to see another thread's write, and the compiler may read the field once and keep it in a register (rule 9). On the course's JDK, the compiled loop does so and never ends. Then declare the flag volatile (TODO 4), which forbids that, and run again: every worker stops. Question 6 of the questions on paper (primitives.pdf) is the same case, as practice.

Part 3: The bounded buffer as a monitorat the keyboard

Example 5 of the slides, in the appendix of block 1, Condition synchronization, which this part assumes. The same class is the one-lock queue that the mini-project starts from.

From the lecture

Every Java object is a monitor: a synchronized method holds its lock, wait() releases the lock and sleeps, notifyAll() wakes every thread waiting on the object. An object has one wait set, so producers and consumers wait in the same set (rule 5). Between the wake-up and the lock, another thread may make the condition false again, and a wake-up without cause is allowed, so the condition is tested again after every wake-up: a while does this, an if does not (rule 4).

The contract

Capacity K, one consumer. put blocks while the buffer holds K items; take blocks while it holds none. Items come out in the order they went in, each exactly once. Everything a producer wrote before put(x) is visible to the thread whose take returns x.

The end of the stream is a convention, not a method: the client reserves a value as the end marker and puts it after the last item; the consumer stops when take returns it. With several producers, the thread that joined them puts the marker.

Exercise 3

Given the ring of slots under the object's lock, with put and take testing each wait condition once with an if, write the two waits as loops, with notifyAll (TODO 1, TODO 2). The end marker is a value the client reserves, BufferCheck.END in the check and Frame.END in the quest; the consumer loop that stops on it is given. Run the check first with the ifs and read the report, then with the loops.

The check: java -cp out BufferCheck: many producers and one consumer that pauses at intervals, so that producers queue at the full buffer. The main thread joins the producers, then puts the end marker. Each put records the order of insertion under the buffer's lock; the consumer must take the items in that order, each once. With the ifs, items are lost, and the report names the wait. With one consumer, the if of take (TODO 2) fails only on a wake-up without cause, which a normal run does not produce, so its loop is required by the contract, not by the check. Then, as an experiment, replace notifyAll by notify in both methods and run: the program may hang, when a wake-up the consumer needed reaches a producer. The check waits 20 seconds from the start of the run, then reports a hang with the waiting threads. After the experiment, notifyAll goes back into both methods.

Part 4: The barrierextensionat the keyboard

Ordering over a whole phase, built on the monitor. Part 5 of the quest uses it.

From the lecture

The lecture builds no barrier; this part builds one on the monitor of part 3. wait() throws InterruptedException when the waiting thread is interrupted: the waiting party catches it, marks the barrier broken, calls notifyAll() and throws the exception again. A party that arrives at a broken barrier throws BrokenBarrierException at once, without waiting.

The contract

new Barrier(parties, action). await() returns only after all parties have called it in the current round. The last party to arrive runs the action once, before any party is released. Everything a party wrote before await, and everything the action wrote, is visible to every party after it. The next round begins at once: a party cannot pass its next await until all parties have arrived again.

If the action throws or a waiting party is interrupted, the barrier is broken for good: the interrupted party leaves with InterruptedException, every other waiting party and every later arrival with BrokenBarrierException. For the parties still waiting, this is the rule of java.util.concurrent.CyclicBarrier.

Exercise 4

Given Barrier with its count of parties, its action and an empty await(), write await() in two steps. First for one round: count the arrivals under the lock; every party but the last waits; the last runs the action, resets the count and wakes the others. Then make it reusable with a round number: a party waits while the round it arrived in is still current. Without the round number, the reset makes a slow waiter's condition true again, so it waits for ever, and a fast party that arrives for the next round corrupts the count. An interrupted waiting party and an action that throws break the barrier, as the contract states.

The check: java -cp out BarrierCheck, two lines. First: a few parties run many rounds at full speed, with an action that counts the rounds; the check records any party that passes before all have arrived, requires the action to run once per round, by the last arrival, and reports a hang at a deadline with the waiting parties. Second: one waiting party is interrupted; it leaves with InterruptedException, the other party and a later arrival with BrokenBarrierException. The check injects no wake-up without cause, so the rounds line cannot catch a single if (...) wait(): the loop is required by rule 4, not by the check.

Quest: A Mini Ray Tracer

The quest starts from a sequential ray tracer in Java. It reads a scene from a text file (spheres, cubes, a floor, lights, a camera) and writes a PNG with shadows and mirror reflections. Six parts make it multi-threaded with the warm-up's structures. Each part has two or three holes: which structure goes where, in what order, and one sentence on why. At the end the program renders in parallel with a correct progress bar, balances the work across threads, and restarts the render when the camera moves. The extensions add soft shadows from many samples per pixel, and a video of a turning cube.

Parts 1, 2, 3 and 6, in that order, are the path; they use Counter and Workers only. Parts 4 and 5 are extensions; part 5 uses Barrier and BoundedBuffer. The lab collects nothing.

The tracer itself, in quest/tracer/, is sealed. The program uses it through this interface only:

The warm-up's four structures, finished or not, go into quest/structures/; the skeletons compile. Then, from quest/:

Render writes render.png. Its options: --part n, how far the program goes; --counter racy|locked|atomic|perworker, the counter the bar reads; --threads n; --out file; --given workers or --given counter,buffer, the finished copies in given/ in place of unfinished structures. Check n runs the check of part n. Each line says pass, FAIL or todo, and a FAIL names the file, the hole and the question to ask. As in the warm-up, a check can show a bug, never prove there is none (rule 8).

The parts accumulate in one Render.java; each part says which lines it replaces. The program rewrites the PNG at intervals during the render, and an image viewer that reloads a changed file (Preview on macOS, most viewers elsewhere) shows the picture grow.

Part 0: The sequential render

The need: java -cp out Render scene.txt renders on one thread: one sample per pixel, jagged edges, hard shadows, one front moving down the picture.

Given the program and scene.txt, change a colour or move a sphere and render again; this part has no hole. The scene file has one object per line: a keyword, then key-value pairs. yaw is the rotation about the vertical axis in degrees, spin the rotation per frame. Part 4 reads samples and a light's radius (soft shadows), and needs tone mapping because light colours exceed 1; part 5 reads frames.

Gives: The baseline, and its time. Each pixel is one call of Tracer.sample, written by picture.set and counted on the counter the bar reads.

Part 1: Workers

The need: The machine has Runtime.getRuntime().availableProcessors() processors, and one of them does all the work.

Given Render.java with the sequential loop over rows and the picture buffer, the bar on the racy Counter, the warm-up's Workers, and the band loop with two holes, write in bands: worker i's band of rows, computed from i, the bands covering every row and the last one taking the remainder, each row rendered by row(scene, y, picture, counter, i); then the join before the PNG is written. Then write, as a comment at hole 1, why no two workers write the same pixel.

As given, the PNG is written at once, grey. With the bands and without the join, it is written with some bands still grey. With both, every band advances at once and the render finishes several times sooner. The bar, still on the racy counter, stops short of 100 %; part 2 repairs it.

From this part on, the bar's thread reads the picture buffer for the preview while the workers write it. This data race on plain ints is accepted: an int is written whole, a stale pixel only delays the preview, nothing is computed from it, and the final PNG is written after the join. The last question of the lab asks for it.

  • hole 1: the band's bounds from the worker's index, and the loop over its rows; then the sentence: no two workers write the same pixel, because …
  • hole 2: the join, before the PNG is written.

The check: the picture equals the sequential one, pixel for pixel. A failure: rows 180 to 224 are unrendered: was every worker joined before the PNG was written, and does every row belong to a band?

Gives: Ownership as the first technique. The picture buffer is shared and unprotected, and correct because each pixel has exactly one writer and no invariant spans two pixels. The join publishes the workers' writes to the main thread (question 1 of the primitives' page).

Part 2: The progress bar

The need: In part 1 the bar stops short of 100 %: twelve threads add to a racy counter while a thirteenth reads it.

Given the bar's loop in Bar.java, which reads the counter at intervals, the option --counter racy | locked | atomic | perworker, and Render.counter, which returns the racy counter for every option, write the choice: one implementation per option, the warm-up's three beside the racy one. Run the bar with each, then write at the hole which counter the bar should use and why, from the contract: what each guarantees, what each costs.

  • hole 3: the counter the option names; then the sentence: the bar uses …, because …

The check: each repaired counter equals the number of pixels after the join, and during the run its get never decreases and never exceeds the adds begun; the racy counter is reported, not judged. A failure: *locked counted 614 400 but a read during the run went backwards: is get inside the lock?*

Gives: The racy bar short of 100 % under a finished picture, the three repairs at 100 %, and a choice among them by cost, since all three meet the contract. n++ on a shared word is three steps, whatever the word's type (rule 3).

Part 3: Load balancing

The need: Static bands are unequal: the bands with the mirror cube and the sphere are still grey when the sky's bands are done.

Given Tiles.java, which replaces the band loop: the picture cut into tiles; a Dispenser whose int next() must hand out each tile index exactly once, given as a plain next++; and a PerWorkerCounter of tiles per worker, read by get(int worker) and printed at the end. Write: first, at the hole of next, a prediction of what two workers running next++ at the same time hand out; then next as one instruction, AtomicInteger.getAndIncrement; then each tile counted for its worker; then the sentence: why one atomic instruction suffices, why no lock is needed, and why a count per worker cannot serve as the dispenser.

The dispenser is not a Counter: neither add and get nor a count per worker can hand out a unique index.

  • hole 4: the prediction, then next as one instruction; then the sentence.
  • hole 5: each tile counted as worker i's on tilesDone.

The check: the check wraps the dispenser, calls next() outside any lock so that the race is not hidden, counts how often each index comes out, and requires every count to be one. The tiled picture equals the sequential one, and the tiles per worker add up to the number of tiles; their spread is printed as an observation. A failure: *tile 1 234 was handed out twice: two workers read the same next; what makes getAndIncrement one step?*

Gives: The atomic counter in a second role: handing out work. A lost increment here renders a tile twice instead of skipping one, so the racy dispenser's picture looks right and only the count shows the race. The printed counts show the imbalance the dispenser absorbs.

Part 6: The explorer

The need: A new camera position should restart the render at once, without waiting for the old render to finish.

Given Explorer.java, with the keyboard read on the main thread, a render on a fresh Workers per camera, one picture buffer reused across restarts, and restart, which only starts the new render, write three lines: the test of stopped() at the top of the tile loop; stop() on the old workers in restart; join() on the old workers before the new ones start.

As given, a new camera starts a second render beside the first, and the two views mix in one picture. With the stop and without the join, the old workers' last tiles land in the reused buffer among the new view's; the check detects them, the eye rarely does. A plain stop flag shows no failure here: the tile loop calls the tracer and the dispenser, after which this JDK reads the field again. The language does not require it (rule 9); the warm-up's empty loop shows the failure.

  • hole 6: the test of the flag at the top of the tile loop.
  • hole 7: stop() on the old workers.
  • hole 8: join() on the old workers, before the fresh ones start.

The check: a scripted camera change in place of the keyboard: after it, no tile of the old view in the picture, and no old worker writing after the new render has begun. A failure: tile (3, 7) holds the old view: were the old workers joined before the new ones started?

Gives: Cancellation and restart in a fixed order: stop, then join, then a fresh start. The volatile flag gives visibility; the join gives ordering. The result is an interactive ray tracer driven from the terminal.

Part 4: Supersampling and tone mapping (extension)

The need: Jagged edges and hard shadows. Many jittered samples per pixel, with lights of non-zero size, give smooth edges and soft shadows. Lights brighter than 1 require tone mapping, which needs the brightest value of the whole picture before any pixel is converted to eight bits.

Given the design: the render is progressive; the outer loop runs over sample passes, and each pass hands out the tiles anew, so the samples of one pixel come from different workers. A single shared film would be written by every worker; each worker therefore has its own film, Film.java, in fixed point. Each sample's channel is capped at radiance 16, rounded to 1/4 096, and added as an integer of at most 65 536 into one int per channel per pixel. With at most 32 767 samples the sum stays below 2³¹: it cannot overflow, and the order of addition does not change it. Also given: ToneMap.java, which maps each band of the merged film by its own maximum, with no fold, which is wrong; and Rng.of(x, y, s), the generator of sample s of pixel (x, y).

Write: the merge of the per-worker films into one, starting from its identity; the fold of the maximum luminance over the bands of the merged film, with its combine and identity, followed by one mapping of the whole film; and, in the samples loop, the generator Rng.of(x, y, s) in place of the worker's.

  • hole 9: the merge, every film added to the zero film.
  • hole 10: the fold of the maximum over all bands, then one mapping.
  • hole 11: the sample's generator, from the pixel and the sample.

The check: the merged film equals the sequential many-sample film exactly, on a reference rendered once at a reduced size: first the sample counts per pixel (the merge and its identity), then the values (the seeding); then the tone map scales the whole picture by one maximum; then the picture on one worker equals the picture on twelve. Failures: pixel (12, 40) holds 23 samples of 24: is the merge adding every film, from the zero film?; band 7 is brighter than it should be: is the maximum folded over all bands before any pixel is mapped?

Gives: A fold with its two laws, combine and identity, and the visible cost of its absence: bands of different brightness. The per-worker film is a design choice, not a repair: a racy shared film would lose a few samples in a hundred thousand, invisibly. Seeding by pixel and sample makes the picture a function of the scene alone, whichever worker renders which tile in which pass.

Part 5: The video (extension)

The need: A cube turns, and its reflection in the mirror cube must turn with it.

Given Video.java, at one sample per pixel, with its design described at the top of the file. The workers live for the whole video. A frame is one buffer whose pixels are owned by tiles, as in part 3. The scene of a frame is an immutable value, Scene.at(k), held in a field that every worker reads and only the barrier's action writes; the same holds for the current frame and the dispenser. For frame k, each worker renders its tiles and arrives at the barrier. The action, run by the last arrival before any party is released, puts the finished frame into the buffer and installs frame k + 1, or the end marker after the last frame. The main thread is the encoder: it takes frames until the end marker, writes each, then joins the workers.

Two happens-before chains carry a frame: the barrier from every worker to the last arrival, and the buffer from the last arrival to the encoder, which is not a party of the barrier. The action's put may block on a full buffer while the other parties wait at the barrier; this is harmless.

As given, there is no barrier: each worker that finishes frame k advances the scene and starts frame k + 1 on its own, and a frame is sent when a plain count says all workers are done. Write: the barrier at the end of each worker's frame, with nextFrame as its action; Frame.END into the buffer after the last frame, and the encoder's loop taking frames until it; and, in place of code, the answer to this question: why do the frames reach the encoder in order, and in which design would the encoder have to hold frames back by number?

  • hole 12: barrier.await() at the end of each worker's frame.
  • hole 13: the end marker after the last frame, and the encoder's loop until it.
  • the question: why in order, and when frames must be held back by number.

The check: the frames arrive in order and each equals its sequential frame; a run that does not end is reported at a deadline. A failure: frame 17 holds tiles from two scenes: what moved the scene before every worker had finished the frame?

Gives: The barrier in its place, and without it a frame torn between two rotations: a fast worker starts frame k + 1 on the advanced scene while a slow one still renders frame k. State shared between phases (scene, frame, dispenser) is changed by one thread inside the barrier. The buffer with its waits in loops and notifyAll (rules 4 and 5), and the hang when the end marker is missing. Ordering of results as a separate concern: settled here by the phases, elsewhere by a sequence number.

The last question and the mini-project

For every piece of shared state in the program, the preview's read included, say which technique protects it: ownership, a lock or an atomic word, or a copy per thread. For every hand-over between threads or phases, say which mechanism orders it: a join, a barrier, a monitor's wait or a volatile flag, and why that one. The sentence holes of the parts answer it piece by piece.

The mini-project rebuilds BoundedBuffer as a queue, three ways: first the warm-up's class as the one-lock queue, with its point of effect named; then a two-lock queue with a dummy node; then a lock-free queue with a lagging tail.
