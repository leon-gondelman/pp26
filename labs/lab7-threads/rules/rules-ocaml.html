Threads in OCaml 5: what to write, what never to write, and why

Programming Paradigms, session 7. Ten rules. Each has a program that breaks it and one that keeps it, in rules.ml, and a line from a run. The run shows the failure; the argument says why. We run them ourselves: ./rules <rule>, or all.

1 every access, or none2 two locked steps are not one3 the plain cell is not atomic4 wait in a loop5 wake everyone6 one lock order7 compare what you read8 a run proves nothing9 a write another thread must see10 how many threads

1. A lock protects data only if every access takes itevery-access

A lock is a rule we follow: every read and every write of the data it protects happens while we hold it. One access outside the rule is enough; the data is then shared with no protection at all, however careful the other accesses are.

let c = ref 0 and m = Mutex.create ()
let inc () = Mutex.protect m (fun () -> incr c)
let add k = c := !c + k          (* forgot the lock *)
let get () = Mutex.protect m (fun () -> !c)
Neverprotect some of the accesses to a piece of data.
Writeone lock per piece of data, named beside it, and take it in every method that touches the data.
Who checksnobody. Rust ties the data to its lock, so that there is no way to reach it without holding it.

One run: broken 775100 of 1000000; fixed 1000000 of 1000000

2. Two locked steps are not one locked operationtwo-steps

A transfer takes from one account and gives to another. If each step takes its own lock and releases it, there is no data race anywhere, and the program is still wrong: between the two steps the money is nowhere, and any thread that looks sees it. The invariant, the total is constant, spans both accounts, so the operation must hold both locks for its whole extent. This is an atomicity violation, and no lock discipline on single accesses removes it.

(* broken *)
Mutex.protect m_from (fun () -> decr from);
Mutex.protect m_to   (fun () -> incr dest)

(* fixed *)
Mutex.protect ma (fun () -> Mutex.protect mb (fun () ->
  decr from; incr dest))
Neverrelease a lock in the middle of an operation whose invariant spans the data it protects.
Writethe invariant first; then choose the critical section so that the invariant is true at its start and at its end, and hold every lock the invariant needs for the whole of it.
Who checksnobody. Not Rust either: this program compiles in safe Rust and is wrong in the same way. A data race is what a compiler can rule out; an atomicity violation is ours.

One run: broken audits that saw a wrong total: 248764 of 250000; fixed audits that saw a wrong total: 0 of 250000

3. The plain cell is not atomicref-not-atomic

An increment is a read, an addition and a write. The atomic cell offers the three as one instruction; the plain cell offers nothing between threads. In OCaml, a ref is a plain cell with no promise at all between domains. Atomic.t offers the whole read-modify-write as one instruction.

let r = ref 0 in
incr r                            (* three steps, a race *)

let a = Atomic.make 0 in
Atomic.incr a                     (* one instruction *)
Neverincr a shared ref.
Writean atomic cell for a counter or a flag; a lock when more than one word must change together.
Who checksnobody. The cost is bounded by the memory model: a wrong number, never a corrupted heap. In C and C++ the same program has no defined meaning.

One run: broken 559811 of 1000000; fixed 1000000 of 1000000

4. Wait in a loop, never in an ifwait-while

A thread that waits for a condition gives up the lock while it waits and takes it back before it goes on. Between the wake-up and the lock, another thread may have taken the lock and made the condition false again. A wake-up with no cause is allowed too. So the condition is tested again after every wake-up, which a loop does and an if does not.

let put b = Mutex.protect b.m (fun () ->
  while b.count = b.capacity do          (* never: if ... then *)
    Condition.wait b.changed b.m
  done;
  b.count <- b.count + 1;
  Condition.broadcast b.changed)
Neverif cond then Condition.wait …
Writewhile not ready do Condition.wait c m done
Who checksnobody. The bounded buffer of capacity one, two producers and two consumers, overflows under the if.

One run: broken stuck at the deadline; overflows 11803, underflows 11879; fixed finished; overflows 0, underflows 0

5. Wake everyone, unless we can argue for onebroadcast

A single wake-up rouses one waiting thread, chosen by the runtime. If the one woken cannot use the news, a producer woken by a producer, the news is lost, and every thread may end up waiting. Waking all costs a few useless wake-ups; each thread re-tests its condition by rule 4 and goes back to waiting if the news was not for it.

Condition.signal b.changed     (* one *)
Condition.broadcast b.changed  (* all *)
Neverwake one thread when more than one kind of thread waits on the same condition.
WriteCondition.broadcast by default; one condition per kind of waiter and signal only with the argument written down.
Who checksnobody. The same buffer, with the loop but signal, stops.

One run: broken stuck at the deadline; overflows 0, underflows 0; fixed finished; overflows 0, underflows 0

6. Take several locks in one order, everywherelock-order

Two threads, two locks, each holding one and waiting for the other: neither can move. Mutual exclusion still holds, nothing bad has happened, and nothing good will ever happen again. Deadlock is a failure of liveness. The classic cure is a total order on the locks, kept by every thread.

(* domain 1 *)                        (* domain 2 *)
Mutex.protect a (fun () ->            Mutex.protect b (fun () ->
  Mutex.protect b (fun () -> ()))       Mutex.protect a (fun () -> ()))
(* fixed: both take a, then b *)
Nevertake lock B while holding A in one place and A while holding B in another.
Writethe order down, by an identifier or an address, and a helper that takes two locks in that order.
Who checksnobody, and no compiler on the table: Rust compiles this deadlock too. A detector can find it after the fact.

One run: broken stuck at the deadline: deadlock; fixed finished

7. Compare-and-set compares what we read, not a value we rebuiltcas-identity

A compare-and-set succeeds when the cell still holds the very object we expect. A value rebuilt from the same number is another object, and the compare-and-set fails although the numbers agree. Every correct retry loop compares against the value it read. OCaml compares by physical equality: a fresh Some 1000 is not the one inside the atomic.

let r = Atomic.make (Some 1000)
Atomic.compare_and_set r (Some 1000) (Some 1001)  (* false *)
let v = Atomic.get r in
Atomic.compare_and_set r v (Some 1001)            (* true *)
Neverpass a literal or a freshly built value as the expected argument of a compare-and-set.
Writelet v = Atomic.get r in … Atomic.compare_and_set r v (f v), and loop on failure. int Atomic.t compares by value, because the number is the object.
Who checksnobody; the type checker accepts both calls.

One run: broken compare_and_set r (Some 1000) (Some 1001) on an atomic holding Some 1000: false; fixed compare_and_set r v (Some 1001) with v the value read: true

8. A right answer in a run proves nothingruns

The racy counter with a thousand increments per thread prints the right number in almost every run; the same program with more increments is wrong in most. The program did not change; the schedule did. Correct means: in every execution. A run can show a bug; only an argument shows there is none.

let cell = ref 0
(* four domains: for _ = 1 to per do incr cell done *)
(* 1000 each: right in most runs; 250000 each: wrong in most *)
Neverconclude from a run, or from a hundred, that a shared structure is right.
Writethe invariant and the point where each operation takes effect; then test with many threads, many operations, many runs, to catch what the argument missed.
Who checksnobody here. Go's race detector reports a race it saw in a run; Rust refuses the data race before any run; for the atomicity violations of rule 2, nobody.

One run: small 1000 increments per domain: wrong in 3 of 100 runs; large 250000 increments per domain, same program: wrong in 10 of 10 runs

9. A write another thread must see goes through an atomicvisibility

A thread that spins on a plain cell written by another thread is a race, and what a race gives is the language's contract to state, not ours to guess. OCaml's memory model promises that a racy read sees a recent write, and the loop ends; the program is still a race, and the promise is about this one pattern, not a licence.

let stop = ref false              (* a race; here it ends *)
let stop = Atomic.make false      (* what to write *)
Domain.spawn (fun () -> while not (Atomic.get stop) do () done)
Neverpass a flag or a result between domains through a ref.
Writean atomic for a flag; a lock, a queue or a join for anything larger. A value published before an atomic write is visible after an atomic read of the same cell.
Who checksnobody. The model bounds the race in time, which is why the loop ended here: read the contract before relying on it.

One run: ref the loop ended: the racy read saw the write; atomic the loop ended

10. An OCaml domain is a core, not a threadmany-domains

The unit that runs in parallel is not the same thing in every language, and the number we may create follows from what it is. Domain.spawn fails after about a hundred: a domain is a unit of parallel execution, meant to be one per core. For many tasks on few cores, a pool over Domain.recommended_domain_count () domains, as Domainslib does, or the lighter Thread, which shares a domain.

List.init 10_000 (fun _ -> Domain.spawn task)   (* fails after ~127 *)
Domain.recommended_domain_count ()               (* 12 on this machine *)
Neverspawn a domain per task.
Writeone domain per core and a queue of tasks, or a library's pool.
Who checksthe runtime, by failing.

One run: broken Domain.spawn failed after 127 domains: failed to allocate domain; fixed Domain.recommended_domain_count () = 12: use that many, and a pool for the tasks
