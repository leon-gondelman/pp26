Part 2 of the course takes four weeks.
Its subject is coordination and communication: how the parts of a program that run at the same time, or on different machines, wait for each other and pass data to each other, and which constructs a language gives us to write that down.

The four sessions are on the slide.
In session 6 one thread runs all our code and a function that waits gives the thread back.
In session 7 several threads run at the same time on the same memory.
In session 8 the parts of a program share no memory and send each other messages.
In session 9 a message can be lost and a machine can stop.

This block shows what the four weeks are about, on one old program and on one small system, a bank.
It explains nothing in depth.

A sequential program and a slow device

Java// k numbers the portions; the bound of portion k is 250000 + 83333 * (k % 3)
for (int k = 1; k <= 8; k++) {
    // a computation: how many primes are there below the bound of portion k?
    String portion = produceNextPortion(k);
    // a slow device: prints the answer as one line of the page
    processPortionTaken(portion);
}


  
A portion is one line of text: the count of primes below a bound, three bounds in turn so that the portions take different times. The device is slow: a pause of 5 to 25 ms before the line reaches the page. Eight lines in order, 220 ms, most of it waiting for the device.

  

    
We start from a program with nothing new in it: a loop that runs eight times.

      Each time it does two things.

      First a computation: it counts how many prime numbers there are below a bound, and writes the answer as one line of text.

      We call that line a portion.

      Then a device prints the portion on a page.

    
The comment above the loop says what k is: it numbers the portions, 1 to 8, and it also fixes the bound.

      There are three bounds, taken in turn, so that the portions do not all take the same time to compute.

      The bounds and the primes mean nothing in themselves: the computation only has to keep the processor busy for a few milliseconds.

    
The device is slow.

      In our program it is imitated by a pause of 5 to 25 milliseconds, different each time, before the line is added to the page.

    
The page has eight lines, one for each portion, in the order 1 to 8, and the run took about a fifth of a second.

      Most of that time the program was doing nothing: it was waiting for the device.

    
This is how a computer of the 1950s spent most of its time: a costly processor standing still while a printer or a card punch, thousands of times slower, did its work.

  







  
Dijkstra’s bounded buffer (1965)

  
  
  
  
  
  
  
  
  
  
  
  
  
  

    

      

        

          

          
E. W. Dijkstra, Cooperating sequential processes, EWD 123, 1965: section 4.3, page 39 of the manuscript. Beside it, the same lines transcribed.

        

        
"begin integer number of queuing portions, number of empty positions,
              buffer manipulation;
      number of queuing portions:= 0;
      number of empty positions:= N;
      buffer manipulation:= 1;

        again 1: produce next portion;

                 P(buffer manipulation);

These lines call acquire.

          
Intuitively, acquire waits until something is available, then claims it:

          
    
            
  • the producer, a free place;
    • 
            
  • the consumer, a portion;
    • 
            
  • each, the right to change the queue.
    • 
          

        

        

          
These lines call release.

          
Intuitively, release makes something available, and a process waiting for it can go on:

          
    
            
  • the producer, a portion;
    • 
            
  • the consumer, a free place;
    • 
            
  • each, the right to change the queue.
    • 
          

        

        

          
Each of those three objects  is a semaphore*: a counter, with two operations:

          
    
            
  • acquire waits until the counter is above zero, then takes one off;
    • 
            
  • release adds one.
    • 
          

          
We come back to them shortly, for what each one allows, but also helps to prevent.

A short history of concurrent and distributed programming

  
  
  
  
  
  
  
  

    
Where does this program stand in history?

      The slide has four lanes: what happened in hardware, in operating systems, in distributed systems, and, set apart at the bottom, in programming languages, which is our lane.

      Time runs from 1950 on the left to today on the right.

    
It begins in hardware, with waiting.

      In the 1950s a processor was costly and its devices, a printer, a tape, a card punch, were thousands of times slower.

      A program that started the printer had to keep asking it whether it had finished, or stopped as soon as it touched the printer again: our first program of today.

      Either way, the device could not tell the processor that it had finished.

      An interrupt changes that.

    
It is a signal from the device to the processor.

      When the device has finished, the processor stops what it is doing, at whatever instruction it has reached, runs a small routine that deals with the device,

      and then goes on with the interrupted program as if nothing had happened.

      So the processor no longer waits for the device: it works, and is told.

    
And for the first time a program is suspended at a point it did not choose, while something else runs.

      Concurrency on one machine descends from that.

    
Once a machine has interrupts, it can run another program while one waits for a device.

      In 1961 this became time-sharing: several people at terminals, each with a program, served in turn by one machine, fast enough for each to feel alone.

      This is concurrency without parallelism: one processor, several activities.

      A few machines of those years had several processors, and they stayed rare for forty years.

    
And in 1972 Unix gained pipes: the output of one program becomes the input of another, with a buffer between them.

      That is the program we just ran, a producer, a consumer and a bounded buffer, offered by the operating system.

  







  
Coordination and Communication

  

  

    
So much for where concurrency comes from.

      Look back at the constructs on that timeline: each of them answers one of two questions.

    
How do processes that run at the same time wait for each other?

      The semaphore and the monitor answer that one.

      How does data pass from one process to another?

      Pipes, communicating processes and messages between machines answer that one.

    
Dijkstra's buffer already has both: its semaphores make the two processes wait for each other, and its queue carries the portions from one to the other.

      Coordination and communication: the two words of the title of Part 2.

      We say what they are on the next slide.

  







  
Coordination and communication

  
  
  
  
  
  
  

    
Coordination: when a process may act depends on what the others have done or are doing.

    

      
not before
P waits until Q has acted

      
    

    

      
not at the same time
P and Q are never both inside

      
    

    
Communication: data passes from one process to another.

    

      
through memory that both can reach
P writes, Q reads

      
    

    

      
by a message
P sends, Q receives

      
    

  

  

    
In Dijkstra's buffer, and in everything on the timeline, there are several processes, and they are not independent: what one may do depends on the others, and they have data to give each other.

      Everything that is new in this part is in these two things, and they give the part its title.

      We first say what they are in general, without any program.

Correctness: safety and liveness

  
  
  

    
“Software is hard.”

    
Donald Knuth

  

  
Writing a correct sequential program is already a challenge. For a concurrent or distributed program it is an order of magnitude harder: one input has many executions, and a part can fail while the others go on.

  

    
In general, the correctness of a program splits into properties of two kinds.

    

      
Safety
Nothing bad ever happens.
A violation happens at one definite moment.

      
Liveness
Something good eventually happens.
No finite beginning of an execution violates it.

    

  

  

    
We have said what the part is about: coordination and communication.

      One general thing remains before we look at the part itself: what all these constructs are for.

      They are there so that the program is correct.

      That was already the aim in Part 1, and it was already hard.

      Donald Knuth, after ten years spent writing one program, summed it up in three words: software is hard.

      Writing a sequential program that is correct, for every input, is a challenge that we never fully leave behind.

Message passing: isolated parts with mailboxessession 8

  
  

    

      
    

    

      
    

  

  appendix
  

    
The other choice is to share nothing.

      The server is cut into parts, and each part owns its data: no other part can reach it.

      The front receives the clients' requests.

      The accounts hold the balance.

      The record keeps the list of what was done, and the notifier tells clients.

      A part can only send another part a message, and each part has a mailbox: a queue where the messages sent to it wait their turn.

    
The accounts take one message from their mailbox, handle it completely, and only then take the next.

      So nothing can touch the balance in the middle of a withdrawal, and there is no lock in the picture.

      The one at a time is now a property of how a part is built.

      The appendix has the slide of session 8, with the bounded buffer on a Go channel and the account as an Erlang process.

  







  
Replication: two copies and a failed linksession 9

  
  
  
  
Two copies cannot reach each other: what does a copy answer to a client? Refuse to answer, or let them differ?

  
  

  
An answer, not a decision: the balance is never wrong, and the client has nothing definitive, neither ok nor refused, for as long as the link is down.

  
Each copy decides from what it knows; a second client withdraws the same 100 at copy 2. When the link returns, 200 has been paid out of 100. Deposits made on both copies add up afterwards.

  
Each copy approves up to its share without asking the other: no failure of the link makes the balance negative. The price: a withdrawal of 100 is refused although the bank holds 100.

  

  appendix
  

    
Last step.

      A bank cannot stop because one machine stops.

      So the accounts are kept on two machines, each with a copy of the balance, here 100, and a link between them over which each tells the other what it has done.

      Between two machines a value cannot be passed as it is: it is turned into bytes, sent, and built again on the other side.

      So between machines only copies travel.

    
Now the link fails: the orange cross.

      Both machines still run, and neither can reach the other.

      A client asks copy 1 to withdraw the last 100.

      What does copy 1 do?

      It cannot know whether the same 100 is being withdrawn at copy 2 at this moment.

      Refuse to answer, or answer and let the copies differ: that was argued in print by people who built real systems, and it is not settled by taste.

The bounded buffer in asynchronous style

  

    

      
 k produced k processed

      

      
 

      
Every run prints portions 1 to 8 in order, each after it is produced.

    

    
Java// one at a time on the queue: one thread runs all of this
static final ScheduledExecutorService loop =
    Executors.newSingleThreadScheduledExecutor();
// producer
static CompletableFuture<Void> produce(int k) {
    if (k > 8) return done();
    String portion = produceNextPortion(k);
    return queue.put(portion)           // wait for room
        .thenComposeAsync(v -> produce(k + 1), loop);
}
// consumer
static CompletableFuture<Void> consume(int k) {
    if (k > 8) return done();
    return queue.take()                 // wait for a portion
        .thenComposeAsync(p -> processPortionTaken(p), loop)
        .thenComposeAsync(v -> consume(k + 1), loop);
}

  

  back
  

    
For the question: what does Dijkstra's program look like in the style of session 6?

      The task and the two functions are those of the first two programs, in Java again.

      What changes is that there is one thread only, here called loop, and that it never stands still waiting.

    
The two labels of the bounded buffer are at the same places.

      Putting a portion in the queue and taking one out no longer make a thread wait.

      Each returns at once with a future: a value that stands for a result that is not there yet.

      What must happen once there is room, or once there is a portion, is given to the future as a function; that is what thenComposeAsync does, and the word loop in it says on which thread that function will run.

      The device is treated the same way: processPortionTaken starts the printing and returns a future that is completed when the line is on the page.

      Each of the two processes has become a function that calls itself for the next portion, because a loop cannot be cut in the middle and continued later; the next block shows how await hides this.

    
The third label is now on the first line, where the one thread is made.

      There is no semaphore and no lock around the queue, because one thread runs everything: two pieces of our code are never inside the queue at the same time.

    
We press Run once.

      The first run appears as a column.

      Then the program is run again and again, one run after the other, and each new run is compared with the first: the line under the columns says which run is under way and whether its order is the same.

      The second run has the same order as the first.

      The third has not, and appears as a second column: in the first run, portion 1 was printed before portion 4 was produced; in the third, after.

    
So on one thread too the order is not fixed by the program.

      But it varies much less than with two threads: in the sixty runs of this series there were two orders, and the runs are not faster than the sequential program.

      The reason is in the first boxes of each column: the one thread computes several portions one after the other, and while it computes it cannot do anything else, not even notice that the device has finished.

      Once the queue is full, the producer waits for room and the consumer waits for the device, so that only one of them can go on at any moment, and the two alternate.

      In asynchronous style, waiting costs nothing, and computing holds everyone up.

Session 9: failure and recovery, which is programming for several machines, where delivery is no longer assumed.

      A message can be lost, a process or a machine can stop, and the rest of the system goes on.

      We look at the form in which a failure reaches a program, and at what the program can do then.

      Why a process that is slow and a process that has stopped look the same from outside: in both cases, no answer has come yet.

      When a request may be sent again: when doing it twice is the same as doing it once.

      And what a restart gives back and what it does not: a process that failed can be started again from a known state, and what it had in memory when it failed is gone.

      Then it gives up.

      The answer is no_answer, after one second.

      The program cannot tell whether the account is slow or gone.

      It also accepts any message as its answer, even a late answer to an earlier request; that weakness is where the question of sending again begins.

    
The second, in OCaml, is two lines in the language of Part 1.

      Each copy of the bank records its deposits as a set of entries, and merge puts two such sets together by taking their union.

    
We run it.

      Merging in either order gives the same set, and merging a set with itself changes nothing.

      So two copies can exchange what they have recorded in any order and as often as they like, and they end with the same record.

      That is how the deposits made on two copies are counted, each once.
