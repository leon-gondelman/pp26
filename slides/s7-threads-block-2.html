Linearizability and progress

correctness and liveness of a concurrent object

The locked stackexample 7a, the reference

JavaOCaml 5
LockedStack.javarecord Node(int value, Node next) { }
Node top = null;   // under the stack's lock
synchronized void push(int x) {
  top = new Node(x, top);
}
synchronized Integer pop() {
  if (top == null) return null;
  Node old = top;

locked_stack.mltype 'a stack =
  { mutable items : 'a list; m : Mutex.t }

Java     popped + remaining = 125000500000
OCaml 5  popped + remaining = 125000500000

Four threads each push 1 to 250,000 and pop after every second push: what was popped and what remains add up to what was pushed, 125,000,500,000.

Each operation holds the stack's one lock for its whole body: pushes and pops run one after another, each taking effect at one instant inside its critical section. In OCaml, Mutex.protect m f holds the lock m for the whole of f.

One run of each is one sample; ten more runs agreed.

HistoriesHerlihy and Wing, 1990

A history records one run as seen from outside: for each operation, the thread that called it, which operation it is with its arguments, the instant of its call, the instant of its return, and the value returned.

Two operations overlap when each is called before the other has returned.

The sequential stack is the specification: a pop returns the most recent push not yet popped, or null.

LinearizabilityHerlihy and Wing, 1990

A history is linearizable, or explained by the sequential stack, when each operation can be assigned one instant between its call and its return, its point of effect, so that the operations taken in the order of these instants form a run of the sequential stack returning what they returned in the history.

An object is linearizable when every history it can produce is.

A history with overlapping pushesthe pops returning 1 and 2

Thread A's pop returns 1, thread B's pop returns 2. Can the sequential stack explain this history?

  1. No: push(1) was called first, so the first pop must return 2.
  2. Yes: the pushes overlap, so push(2) may take effect first; the pops then return 1, then 2.
  3. No: the sequential stack explains no history with overlapping operations.
No client can tell which push took effect first: the locked stack itself produces this history when thread B takes the lock first.

Progress conditionsHerlihy, 1991 and 1993

Blocking: a thread's progress in an operation can depend on another thread's being scheduled. Thread A holds the lock and is stopped: B and C wait for ever.

Lock-free: from any point on, as long as some thread keeps taking steps inside an operation, some operation completes within finitely many steps, whichever threads are stopped and whenever. B keeps completing; each of B's successes fails C's attempt, and C starves.

Compare-and-set

an atomic read-modify-write, retried on failure

The counter on compare-and-setexample 6

JavaOCaml 5
CounterCas.java// n: an AtomicInteger, from 0
static int increment() {
  int failed = 0;
  while (true) {
    int v = n.get();             // read
    if (n.compareAndSet(v, v+1)) // still v?
      return failed;             // wrote v+1
    failed++;                    // retry
  }
}
counter_cas.mllet n = Atomic.make 0

let increment () =
  let rec attempt failed =
    let v = Atomic.get n in           (* read *)
    if Atomic.compare_and_set n v (v + 1)
    then failed                 (* wrote v + 1 *)
    else attempt (failed + 1)         (* retry *)
  in
  attempt 0
Java     got 2000000, failed attempts 653147
OCaml 5  got 2000000, failed attempts 679563
fetch-and-add: got 2000000 in both

Two threads, a million calls each. Can the total be wrong, and can an attempt fail?

  1. exact; no attempt ever fails
  2. exact; an attempt fails when another thread wrote since its read
  3. wrong whenever an attempt fails
A failed attempt loses no increment: the loop reads again. Fetch-and-add, the last line, never retries.

Compare-and-set with retrythe second way, in the four terms

The contract. The operation is atomic without exclusion, and linearizable: its point of effect is the compare-and-set that succeeds.

The obligation. Every attempt starts from a fresh read; every write keeps the invariant, here that it replaces v by v + 1; the programmer names the point of effect.

Compare-and-set with retrythe progress risk; who checks

The progress risk. A compare-and-set fails only because another succeeded, so operations keep completing: lock-free. Not wait-free: a thread may retry without end while the others keep completing operations. Fetch-and-add takes no expected value, so it never fails: wait-free, each call one step.

Who checks. Nobody but the programmer, by proof; Java and OCaml accept a loop that keeps an old value, or two atomic steps meant to be one.

PART 3

Treiber's stack

a lock-free stack on one atomic reference

Treiber's stackexample 7b: push and pop as compare-and-set loops

JavaOCaml 5
Treiber.javarecord Node(int value, Node next) { }

static void push(int x) {
  while (true) {
    Node old = top.get();
    Node fresh = new Node(x, old);
    if (top.compareAndSet(old, fresh))
      return;  // point of effect: the CAS
  }
}
static Integer pop() {
  while (true) {
    Node old = top.get(); // effect if empty
    if (old == null) return null;
    if (top.compareAndSet(old, old.next()))
      return old.value(); // effect: the CAS
  }
}
treiber.mltype 'a stack = 'a list Atomic.t
(* the list is never changed, only replaced *)

let rec push (s : 'a stack) x =
  let l = Atomic.get s in
  (* point of effect: the compare-and-set *)
  if Atomic.compare_and_set s l (x :: l)
  then ()
  else push s x                    (* retry *)

let rec pop (s : 'a stack) =
  match Atomic.get s with
  | [] -> None       (* effect if empty *)
  | x :: rest as l ->
      if Atomic.compare_and_set s l rest
      then Some x      (* effect: the CAS *)
      else pop s

top is an atomic reference; the nodes are immutable, a record's fields being set once. The invariant: top points to a well-formed stack, a chain of nodes ending in null, in OCaml a list.

A push builds its node outside the stack, pointing at the top it read, and replaces top by it with a compare-and-set, which succeeds only if top is still the one it read; otherwise it reads again and builds a new node.

Four threads push only, a million pushes in all. Where does it go wrong, and is it a data race?

  1. between its read and its write another push took effect, and the write loses it; not a data race, both accesses being atomic
  2. the read and the write are a data race with the other threads' writes, since nothing orders them
  3. the immutable nodes are the problem: a node cannot be re-pointed at a new top
The bug is the racy counter's: a step of another thread falls between a thread's read and the write that depends on it. An atomicity violation without a data race.

Proof sketch for Treiber's stackthe invariant; the points of effect

The invariant. top points to a well-formed stack, the list of values from the top node down to null. It holds at the start; every write to top is a compare-and-set that keeps it; a failed attempt writes nothing.

The points of effect. For a push, the compare-and-set that succeeds. For a pop on a non-empty stack, the same. For a pop on an empty stack, the read that saw top null.

Proof sketch for Treiber's stacksafety; liveness

Safety. In the order of the points of effect, the operations form a run of the sequential stack: between two of them top does not change, and each does one sequential push or pop and returns what it returns.

Liveness. An attempt fails only because another thread's succeeded since its read, and each success completes an operation; so operations keep completing: lock-free, and not wait-free.

appendixthe ABA problem: a top that changes and comes back, with a garbage collector and without

Persistent data structures and compare-and-setHerlihy, 1993

A persistent structure keeps its old version usable after an update; the new version shares the unchanged part. Treiber's stack is such a value behind one atomic reference, and a read of the reference is a snapshot of the whole stack.

Herlihy, 1993. Read the reference, apply the operation to a copy, swing the reference to the copy with a store-conditional, which fails if anything wrote since the read; retry on failure.

Persistent data structures and compare-and-setClojure's atom

Clojure's swap! applies a function to the value in an atom, an atomic reference, by that protocol on compare-and-set: read, apply, compare-and-set, retry.

Under contention the function runs several times: in three runs, 800,000 swaps ran it between 4.2 and 4.6 million times. So it must have no effects, and nothing checks it. Java's updateAndGet is the same loop with the same warning.

PART 4

Contention

the cost of retry

Lock-free against lock-basedcontention

Contention. Several threads want the same word at once: one attempt succeeds, the rest are wasted work, and every operation on the stack passes through the top. An uncontended lock costs one step, like one attempt.

Flat combining. Each thread publishes its request; one thread, under a coarse lock, performs them all: lock-based, blocking, and faster (Hendler, Incze, Shavit and Tzafrir, 2010).

OCaml 5  got 2000000

Each thread counts in a variable of its own; the order in which the threads run cannot matter, because no location written by one thread is read or written by another while they run.

The argument rests on the join, which orders each thread's write of its element of counts before the main thread's read. Without it the program has a data race and may print 0, one million or two million.

In Rust the compiler checks that nothing is shared, by giving each slot one owner; in Haskell the types do, since a pure function cannot write a cell. In Java, nobody does.

The parallel foldexample 8 (b) and (c): 1 to 8 from 0, with + and with −

A fold combines the elements of a sequence with an operation, one after another from a starting value, the seed. Here the sequence 1 to 8 is cut into parts; each part is folded from the seed 0 on a thread of its own; after the joins the parts' results are combined with the same operation, in the order of the parts.

+ in two halves 36, in four quarters 36
- in two halves 16, in four quarters  0
Java and OCaml 5 print the same

The sequential fold with subtraction, one thread from left to right, gives −36. Which is true of the parallel fold?

  1. it agrees in two halves and in four quarters, and the answer is the same on every run: the threads only share the work
  2. it agrees in neither, and the answer is the same on every run
  3. it agrees in neither, and the answer changes from run to run: it depends on which thread finishes first
With subtraction the answer depends on how the sequence is split, never on which thread finishes first. If the operation has no side effects and is associative, every part is folded from its identity, and the parts are combined in their order, every split gives the sequential fold's answer.

Two bracketings of one foldsubtraction on 1 to 8

The parts are the same numbers in the same order; only the bracketing differs, and the roots differ. With addition both roots are 36, as is the sequential fold, because addition is associative.

The forms of the third wayindependent parts; commuting updates

Independent parts and a combine step. No location written by one thread is read or written by another while they run; the combine has no side effects and is associative with an identity, and the parts are combined in their order.

Commuting updates. Each update is one atomic step, or goes to a replica merged at the end; the interleaving orders the steps, and commutativity makes the final state the same for every order.

The forms of the third waydeterminism by construction; immutability

Determinism by construction. A dataflow network, sequential programs connected by queues with one writer and one reader each, computes the same function in every schedule (Kahn, 1974); single-assignment variables do the same.

Immutability is not a fourth way: it serves the second, Treiber's nodes and copy-and-swap, and the third, nothing shared because nothing mutable.

The counter and the stack comparedwhich work the third way is for

The counter. Increments commute: applying them in any order gives the same total. So when each increment is atomic, under a lock or by one instruction, or is made in a slot of its own, every way gives the same final value.

The stack. Two pushes on a shared stack do not commute, and the pops show which came first: the result depends on the interleaving under every way; the only demand on it is linearizability.

The two balances add up to 200 between transfers. A reader holding both locks sees 199: it read between the two halves of a transfer. Two atomic steps are not one atomic step, under locks or under compare-and-set.

Two linearizable objects used together are a linearizable system, each operation at its own instant: Herlihy and Wing's locality. What is not given is one instant for two operations: the withdrawal and the deposit each have theirs.

PART 7

Memory models

sequential consistency for data-race-free programs

The memory model's guaranteethe fourth assumption, with its condition

There is one memory, and every read returns the value of the latest write before it in the interleaving (Lamport, 1979: sequential consistency). The language guarantees it for every program none of whose interleavings has a data race, with its atomics in the strongest mode.

Why a guarantee. Processor and compiler reorder reads and writes for speed. Adve and Hill, 1990: a race-free program still runs as one sequence; the language's memory model says so.

The memory model's guaranteethe session's programs

What made the session's programs race-free. In the spin lock, the order test-and-set gives between one thread's release and the next's acquire; in the count per thread, the join; in the loop and Treiber's stack, every access to top atomic, the nodes published through it.

The guarantee applied to them: every run behaved as an interleaving; the reasoning by interleavings was sound.

The transfers take their locks in a global order; the reader takes none. Its two reads are each a data race. What does the language guarantee for it?

  1. nothing: a racy program has no meaning in any language
  2. every run is some interleaving: the transfers are locked
  3. no guarantee of an interleaving; what remains is set by each language's memory model, and in Java and OCaml 5 a race is bounded
C and C++: undefined behaviour. Java: a read returns a value once written to that variable, bounded in space. OCaml 5: also bounded in time. Go: like Java for one word. Safe Rust: no data race can be written.

APPENDIX

Progress, universality and composition

wait-free; the ABA problem; the whole structure; consensus numbers; transactions; the languages compared

Progress conditionswait-free; the clause

Wait-free: every thread that keeps taking steps inside an operation completes it within a finite number of its own steps, whichever other threads are stopped and whenever. B and C both complete.

The clause "whichever threads are stopped" is what makes these conditions about progress: without it a lock would count as lock-free, since a holder that is allowed to run finishes.

back

Construction and progress

Lock-based and without locks say how a structure is built; blocking, lock-free and wait-free say what progress it guarantees, and nothing else. A lock-based structure is never lock-free.

A structure built without locks is not thereby lock-free: the Disruptor, a queue over a ring buffer, has no lock on its path and still blocks.

back

The ABA problemthe hazard; on this stack

The hazard. A thread reads a location as A; other threads change it to B and back to A; the thread's compare-and-set, expecting A, succeeds although the structure it reasoned about may have changed.

On this stack. A push and a pop between the read and the compare-and-set leave the very node read at the top again: harmless, since that node, never changed, heads the same chain.

back

The ABA problemwith a collector; without one

The garbage collector. A node any thread still holds is never freed, so its address is never reused, and every push allocates a fresh node: a different node at the same address cannot arise.

Without a collector. In C or C++ a popped node may be freed and its memory reused. A stale pop may read next from freed memory, a use after free, or, as here, install a freed node as the top. Hazard pointers and epochs delay the freeing of a node until no thread can still hold it.

back

Lock-free against lock-basedthe whole structure; the progress guarantee

Operations on the whole structure. Where nodes change in place there is no instant at which the whole is unchanged: Java's ConcurrentLinkedQueue.size traverses and may be inaccurate. A persistent value behind one reference has that instant, the read of the reference.

Progress guarantee. A stopped lock holder stops every waiter; a thread stopped in mid-push stops nobody. Where that must hold, only a non-blocking structure will do.

back

Universality of compare-and-setHerlihy, 1991

Every structure. With compare-and-set, every object with a sequential specification has a wait-free, linearizable version; with reads and writes alone, not even a stack that two threads share.

The construction. Every operation is appended to one shared list, which every thread applies in the same order to a copy of its own; a thread that appends also appends the operation of the thread whose turn it is. Nothing runs in parallel.

back

Ways to composelocks; one reference

Locks compose by hand. Both locks around both steps make the transfer one operation, at the cost of deadlock and a global order of the locks.

One compare-and-set covers one reference. Both accounts behind one reference to a persistent dictionary: the transfer is one compare-and-set, and every update of the dictionary competes for that reference, the cost of Clojure's atom.

back

Ways to composetransactions

Transactions compose, lock-based operations do not (Harris et al., 2005). A transaction's writes take effect together, at one instant, or not at all; on a conflict the runtime reruns it.

In the course's runs, Haskell's counter under atomically was exact in ten runs of ten; in Clojure, with 800,000 transfers in one dosync each, a reader inside a transaction was never wrong and a reader outside one was wrong 5,345 times.
