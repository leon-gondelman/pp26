Asynchronous programming

concurrency on one thread

What does a program do while it waits, and where is the rest of a function while it waits?

The first block ended on this question: a program sends a request and must wait for the reply;

what does it do meanwhile,
and where is the rest of the function that was in the middle of its work?

This block answers the first half, for one model of computation: one thread runs all our code,
and the sources of events, the clock, the network, the disk, lie outside it.

We state what this model guarantees, as four properties, and we name them with the terms of the field.
Then we watch three small programs run under these properties, and predict each before it runs.

No mechanism in this block: we state what a language with async and await guarantees.
What the suspended function is, who holds it and who resumes it is on the page of the lab's optional quest.

PART 1

The model and its properties

one thread, four properties

The model and what it guarantees, stated as four properties, in the terms of the field.

One slide runs programs, the callbacks slide; the others state the model and its properties.

About twenty minutes: the model and the callbacks slide are brief; the properties take the time. Other languages are part 3.

The modelone thread, a stack, a heap, a queue, and a host

Call stack: one frame per call that has not returned: its arguments, its local variables, where to return.
Only the frame on top executes.

Stackless: at an await the frame is popped and its state kept in the heap; one frame is saved.
Goroutines and Java’s virtual threads are stackful: the runtime keeps the whole stack.

Heap: every value that must survive after the frame that created it is popped.
Objects, closures, and the saved state of a suspended function: its local variables and where to resume.

The crux of asynchronous programming: the rest of a function becomes a value.
As a value it can be kept in the heap, with its local variables and the point where to resume.

Queue: the functions that are ready to run and have not run yet.

The queue holds work, not data: a function ready to run, which points to what it needs in the heap.
Nothing moves from the heap to the queue.

Loop: when the stack is empty, takes one function from the queue to the stack and runs it to its end.

When a value arrives, the host queues a function that stores it in the heap.
That queues the rest of the waiting function, which the loop then runs.
The heap remembers, the queue schedules, the loop dispatches, the stack runs.

Host: the browser or the operating system.
It owns the clock and the devices, and it can only append a function to the queue.

A browser appends the function that answers user input, a timer that is due, a network reply, a message.
What resumes after an await goes to a second queue, the microtask queue; we will see both.

A model of what the language guarantees, not of how an engine is built. Two assumptions hold for the whole block.

One thread: all our code runs on it; no other thread runs code of ours.

An uncontrolled environment: the order of the host’s events is not the program’s to fix.

The runtime of the model has four parts. It is a model of what the language guarantees, not a description of an engine: V8 or SpiderMonkey keep a suspended function in their own form; what matters is that enough state is kept to resume it, and where it waits.
A call stack holds one frame per call that has not returned: its arguments, its local variables and where to return; only the frame on top executes.
A heap holds every value that must survive after the frame that created it is popped: objects, closures, and, as we will see, the saved state of a suspended function, its local variables and where to resume.
A queue holds functions that are ready to run and have not run yet.
And the host, a browser or an operating system, owns the clock and the devices.
The host does its own work outside this thread. It cannot call into our program: when its work is done, it can only append to the queue a function that calls ours, the callback we gave it or the resolution of a promise.
The loop takes one function at a time from the queue to the stack and runs it to its end.

This structure, a stack, a queue of pending deliveries and a heap served by one thread, is what Miller, Tribble and Shapiro called a vat in 2005, and they call it the classic event-loop model.
The program on the left is the one we follow through the block: load prints A, asks for a user and prints C with the name; its caller prints B.

If asked: is the queue first in, first out? In the model, yes. JavaScript keeps two queues, one for the host's functions and one for the continuations of promises, and empties the second fully after each function of the first; the demo shows both, and the difference plays no role today.
If asked about other threads: Node uses a pool for files and name resolution; none of those threads runs code of ours, which is the first assumption.

Definition. An asynchronous function can be suspended at the points marked await in its text. At a suspension point its frame leaves the stack; the part that remains to be run, with its local variables, is kept in the heap. The caller resumes.

The word promise is Friedman and Wise’s, 1976, for a lazy suspension; Baker and Hewitt’s future, 1977, is eager; Liskov and Shrira, 1988, gave the promise its typed form for asynchronous remote calls.

The rest, the highlighted line, is kept, registered on the awaited promise: a value that stands for a result to come.

The rest is a function of the awaited value: user => { console.log("C", user); }

Running: on the stack. Suspended: waiting for a value that is not there yet.
Ready: in the queue, its value there, waiting for the loop to run it.

Control passes only where the text says so, at an await: cooperative (Adya et al., 2002).
Threads are preemptive: control can be taken away between any two instructions.

Property 1 · Suspension. An asynchronous function is suspended only at an await written in it. Its caller then goes on with its next statement: after load(); the script prints B.
A caller that writes await load(); is suspended too.

The definition, on the left.
An asynchronous function, async function in JavaScript, async def in Python, is a function whose activation can be suspended at points marked in its text by await.
At a suspension point its frame leaves the stack; the part of the function that remains to be executed, with the values of its local variables, is kept in the heap.
The function's caller resumes.
The activation is later resumed: the kept part returns to the stack and execution continues after the await, with the awaited value in place.

A function that is called runs at once, inside its caller, up to its first suspension point; what it leaves behind at that point is a promise, a first-class value that stands for its eventual result.
The word is Friedman and Wise's, 1976, for a lazy suspension; Baker and Hewitt's future, 1977, is eager; Liskov and Shrira, 1988, gave the promise its typed form for asynchronous remote calls. A JavaScript promise is eager.

If asked: what does load return? A promise for its own result, pending until the rest of load has run. Two promises are in play at the await: the one load awaits, and the one load returns to its caller.
If asked: what is the kept rest, concretely? A function with the values of its variables, a closure; the appendix shows it written by hand, and how a compiler produces it from the function's text.

appendix

The two ends of one promise. new Promise makes a promise and hands us the function that settles it; await waits on a promise. The promise in the heap connects them.
new Promise creates a pending promise and calls the executor at once, synchronously, with res. Here the executor gives the host a timer of 300 ms whose callback calls res("Ada"). new Promise is how a host's callback interface, setTimeout here, becomes a promise.

If asked: what about the second argument of the executor? It is rej: rej(e) rejects the promise with the error e, and an await on a rejected promise throws e at the await. Failure is not treated in this session.
If asked: does res(v) always fulfill? When v is a plain value, yes. Strictly res resolves: if v is itself a promise, ours follows it, and is fulfilled only when v is.
If asked: where is new Promise in load? Nowhere in our text: calling an async function creates its own promise, and its return settles it. In await fetchUser() the promise is fetchUser's; the caller of load gets load's.
The dagger: the pair is not JavaScript's; every language with async and await has a result that starts pending, is settled from outside by whoever holds the setter, and is awaited. What differs is around it: whether the call starts the work, whether await suspends on a value already there, which thread resumes; part 3, and the appendix table. Python: fut = loop.create_future(), fut.set_result(v), await fut. C#: var tcs = new TaskCompletionSource<T>(), tcs.SetResult(v), await tcs.Task. Rust (tokio): let (tx, rx) = oneshot::channel(), tx.send(v), rx.await; there the future runs only when polled, as part 3 shows.
If asked: can we wait without await? Yes, with then; the appendix builds then and a loop by hand, and await as a generator with a driver.

Callbacksthe rest of a computation, passed by hand

Before promises, a function whose result comes later took a callback: the rest of the computation, as a function, which it calls with the result.

  1. Nesting: each step is written inside the callback of the step before. With await, the steps follow one another.
  2. No composition: a result not yet arrived is not a value; waiting for two takes a counter. A promise is a value: stored, passed on, awaited by several.
  3. Inversion of control: the function we call decides when our callback runs, and how many times. A promise is settled once, and what waits on it always goes to the queue.
  4. Errors: an exception thrown in a callback does not reach the caller’s try. Failure: session 9.

Execution: one sequence of resumptions. One program and one input have as many executions as the environment can produce.

    

      
Not a stack: P was suspended first and resumes first, while Q waits. No single stack can hold both: each saved state is in the heap.

    
Interleaving points are exactly the suspension points. Between two of them, nobody else runs.

    

  

  
Property 4 · Atomicity between suspension points. A stretch of a function’s text with no await in it is atomic with respect to all other code of ours: nobody observes it half done, except the functions it calls, which run inside it; others run only between stretches. Atomic: isolated, not all-or-nothing.

  

    
From the previous slide: running code is never interrupted. So the only places where another computation can slip in are the points where ours gives the thread back: the awaits. What that means for two computations side by side.

    
Two computations, P and Q, each suspended at an await, each resumed when its value arrives.

      Blue is running, hatched is waiting. The order of the arrivals is the environment's: here P's value first.

      With several pending computations, which one resumes next is decided by the arrival of its value, and arrivals are the host's.

    
If asked: is this not determinism? Given the arrivals, yes: the loop's choices follow from the queue. The arrivals are not ours, and that is where the executions differ.

      If asked: why not call it a data race? Because no two accesses are ever concurrent on one thread. Next week the same program on two threads has one.

      Go and Java's virtual threads have none either: the waiting code blocks, and the runtime parks the goroutine or virtual thread with its whole stack.
