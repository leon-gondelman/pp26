PART 1

Two definitions of computing

1936, before any computer

What is computing?

Two answers, both from 1936:

a processor executing instructions and changing the state, step-by-step, using a transition functionTuring
a calculus transforming a program, according to a rewriting relation, to evaluate a function applied to its argumentsChurch


imperative/functional stylea global state, changed by assignment and sequencing (von Neumann 1945)expressions and application, no state (Lisp 1958, ML 1973)
machine/calculus modelan operational model of how — the tool of complexity theoryan equational model of what — the foundation of language semantics (Landin 1964, Scott 1970, Plotkin 1975)
explicit/implicit controlthe order of the steps is written: ";", loops, the program counterthe order is not written: a strategy chooses — this session
Collect answers from the room first; they fall into the two rows. The universal machine (a program as data on the tape) and "a recipe: mechanical steps" are common to both definitions and are said on slides 5 and 7, not here. The first two contrasts are the textbook ones; the third is this session's, stated with the machine on the left like the others — explicit control on the imperative side, implicit on the functional side. The next two slides give it its mathematical form: a transition function versus a reduction relation.

Turing, 1936: a machine

  • a finite set of states
  • a tape of cells, unbounded, one symbol per cell
  • a head that reads one cell
  • one rule per state and symbol: write, move, next state
statereadswritesmovesnext
go11→go
go␣1←back
back11←back
back␣␣→halt

A machine that adds one to a number written in unary.

Control is a position: the state and the head. The next step is a function of them: exactly one move.
On computable numbers, 1936, published 1937. The machine is the imperative paradigm before any imperative language: a global state, one step at a time, the next step fixed by where we are. Turing's own distinction in the paper: automatic machines, whose motion is completely determined by the configuration — these define computing — and choice machines, where an external operator decides at some points. The universal machine, which reads another machine's table from its tape, is the program as data: the stored-program computer nine years early.

Church, 1936: a calculus

Terms are built from three forms:

  • a variable — x
  • a function — λx. t
  • an application — t u

One rule: an application is replaced by the function's body, with the argument put in for the variable. A term can offer two places to apply it:

        (λx. x + x) (2 × 3)
   argument first ↙       ↘ function first
   (λx. x + x) 6       (2 × 3) + (2 × 3)
        ↓                     ↓
      6 + 6              6 + (2 × 3)
        ↓                     ↓
       12                   6 + 6  →  12

Numbers, + and × are not part of the calculus; they keep this first example readable. Block 2 defines numbers from the three forms.

Control is a choice: a step is allowed at any application; nothing in the term picks one. The next step is a relation — a strategy makes it a function (block 2).
An unsolvable problem of elementary number theory, 1936. No state, no tape, no order written down: the term does not say which of its two applications goes first. Left: the argument first — three steps, one multiplication (block 2: applicative order, call-by-value). Right: the function first, the argument substituted unevaluated — four steps, the multiplication twice (normal order, call-by-name). Same answer either way; block 2 shows the term where only one way reaches an answer. That silence is the whole of this session. Function versus relation is the literal mathematical difference between the two definitions, and it is standard in PL theory in these words: a reduction strategy turns → into a function (Plotkin 1975; Barendregt 1984, ch. 13). Church–Rosser: the choice can cost steps or the answer's arrival, never the answer. If asked how this relates to functional programming and to "no loops, only recursion": block 2, the slide "Control as syntax, control as a value" — no control syntax, so control lives in values, and the values are functions.

Different answers, same expressive power

  • Turing, 1937, in an appendix: every function the lambda-calculus defines, a machine computes, and the other way round.
  • Kleene, 1936: a third definition, recursive functions — the same functions again.
  • Every definition of "computable" proposed since computes the same functions. This is the Church–Turing thesis.
Equal in what they can compute. Differerent in one design decision: who decides the next step.
The thesis is not a theorem: it says that the informal notion of "effectively computable" is captured by these definitions. Every language we use is equivalent to both, so the choice between the two paradigms is never about power.

The two definitions, as machines and as languages

Paradigm ≠ language: Java has lambdas, OCaml has for. A language makes one of the two the default.

Backus 1978 called the left column the von Neumann bottleneck: one word at a time through the program counter. The right column is what "functional" means before any feature list: a program is an expression, running it is reducing it.
PART 2

Recursion and the stack

What does a machine need to call a function?
A call also needs an order and a passing mode for its arguments — part 4, separately.

A call, on the machine

int sum(int *a, int n) {
  if (n == 0) return 0;
  return a[0] + sum(a + 1, n - 1);
}

sum calls itself before it can add. The machine must remember, for every call not yet finished three things:

  1. where to continue — the return address
  2. the arguments — a, n
  3. what is left to do — 3 + _

One such record is a frame. Frames are pushed at a call and popped at a return: the call stack.

The machine does not substitute. It stores: the argument in the frame, and what remains to be done on the stack.
Session 2's stack, used by every compiled language since Algol 60 (Dijkstra's proposal). The frame is the machine's environment; the pending "3 + _" is the machine's context. Both words return in the lab.

The same call, in the calculus

The stack holds what the calculus keeps in the term: the surrounding computation. Same information, two places.
Step it. Left: a frame per call, each with its pending addition. Right: the term grows one "3 + (" per call and collapses from the inside at each return. The two columns move in lock-step; that is the slide.

Can a loop replace every recursion?

A tree 100 000 notes deep. Right: session 2's stack in a new job — Lab 2's maze visit was this loop.

Both run here, in Python (Pyodide): the left one fails at Python's own limit, the right one counts 100 001 notes. The explicit stack is the recursion's stack made visible; the order we push the children is the order they are counted — depth first, as in the maze.

What the explicit stack holds

def count(m):
    n, stack = 0, [m]
    while stack:
        m = stack.pop()
        if m[0] == "Note": n += 1
        else: stack += [m[2], m[1]]
    return n
Each entry is what to do next once the current subtree is counted — the rest of the computation. Session 5 names it: a continuation. Sessions 6 and 7 hand it to a scheduler: a thread is a stack the operating system saves; a coroutine is a stack the program saves itself.
Reynolds 1972, definitional interpreters: making the stack explicit is the first step from a recursive evaluator to a machine. Said, not proved; three sessions pay it back.

Does a tail call need the stack?

let rec sum acc = function
  | [] -> acc
  | x :: xs -> sum (acc + x) xs

sum 0 [3; 1; 4]      (* 8 *)

After the call, nothing is left to do: no pending 3 + _. The accumulator carries what the stack would have held.

let sum xs =
  let acc = ref 0 and l = ref xs in
  while !l <> [] do
    acc := !acc + List.hd !l;
    l := List.tl !l
  done; !acc

The compiled code of the left is the right: the frame is reused, the call becomes a jump.

* A tail call is a call in the position where its result is returned unchanged.

Steele 1977: a procedure call is a goto that passes arguments; the "expensive procedure call" is a myth of bad compilers. The accumulator is the loop variable; the arguments of the tail-recursive function are the state of the loop.

Proper tail calls are a language decision

guaranteednot guaranteed
Scheme — a requirement of the standard since 1975Python — refused on purpose: the traceback would lose frames
OCaml, Haskell, Erlang — every loop is written this wayJava — the JVM has no tail-call instruction
Lua, ElixirC — an optimisation the compiler may or may not apply
Whether a tail call needs a frame is decided by the language, not by the program. Same program, two behaviours.
Clinger 1998 gives the definition as a space guarantee: a tail-recursive loop runs in constant stack. JavaScript: ES2015 requires it, only Safari implements it. C: gcc -O2 does it for the simple cases; -O0 does not.

Recursion and loops, stated

loop → recursionEvery loop can be written as a tail-recursive function: the loop variables become its arguments.
recursion → loopEvery recursion can be written as a loop with an explicit stack: the stack holds the pending work.
Equal power; the difference is what the program writes down and what the language keeps hidden. Compilers perform both translations: a tail call becomes a jump, a recursion becomes a loop over an explicit stack — a stack of continuations, session 5.

Sources: recursion elimination — Bird 1977; the construction — Reynolds 1972; a tail call as a jump — Steele 1977.

Not a theorem with one name. Böhm–Jacopini 1966 is the neighbouring result and says something else: sequence, selection and iteration suffice to replace jumps. The first line is what a functional language does with every loop; the second is what a compiler does with every recursion. Neither paradigm can do something the other cannot; each makes one of the two directions invisible.
PART 3

Implicit control: the loop as a value

Do we need a loop construct at all?

Observation: one recursion, three bodies

let rec sum = function
  | [] -> 0
  | x :: xs -> x + sum xs
let rec product = function
  | [] -> 1
  | x :: xs -> x * product xs
let rec length = function
  | [] -> 0
  | x :: xs -> 1 + length xs

Three functions, one recursion. What differs: the value for [], and how x is combined with the result for the rest.

If the two differences were arguments, one function would do for all three.

Session 3's count_notes is the same recursion on a tree. Read the accented parts aloud: a starting value and a combining step; everything else is the walk over the list.

The body as a parameter: fold

let rec fold f acc = function
  | [] -> acc
  | x :: xs -> fold f (f acc x) xs

let sum    = fold (fun acc x -> acc + x) 0
let length = fold (fun acc _ -> acc + 1) 0

The loop is now a value: the recursion is written once, in fold; a use writes no control at all — we pass it, name it, return it.

A function that takes or returns a function is higher-order; functions are first-class values.

let compose f g = fun x -> f (g x)       (* takes two functions, returns one *)
let evens_squared = compose (List.map square) (List.filter even)

Session 3’s sets-as-objects (Way 2) were already this: a set was a function, and insert returned one.

Session 5: who drives a loop — the collection (fold) or the caller (iterators, generators) — and control as a value the program passes: closures, thunks, continuations.

Next: how fold runs, step by step.

fold is the tail-recursive sum of slide 17 with the body abstracted. Nothing new was added to the language: functions were values since session 3's JavaScript sets. Session 5 writes fold, map and filter from scratch; today we use them.

Two folds: the order in which f is applied

let rec fold_left f acc = function
  | [] -> acc
  | x :: xs -> fold_left f (f acc x) xs

f runs as soon as an element is met, from the left, and its result is carried along as acc.

The recursive call is the last thing done — a tail call, like sum acc on slide 17. The frame is reused: a loop, no stack.

let rec fold_right f xs z = match xs with
  | [] -> z
  | x :: xs -> f x (fold_right f xs z)

f runs only after the rest of the list is done, so the first application to run is the last element's — from the right.

The recursive call is inside f x _: not a tail call. One pending frame per element — the stack of slide 13.

Two orders of applying the same f: left to right with a carried value, or right to left with pending work.
Read the two definitions aloud and point at the position of the recursive call: outside f on the left (tail), inside f on the right (pending). That is the whole difference, and it is the loop-versus-stack difference of part 2 again.

Same f, same list — two answers?

With f = (+), z = 0:

fold_left:   ((0 + 3) + 1) + 4  =  8
fold_right:  3 + (1 + (4 + 0))  =  8

The same result: addition does not care where the parentheses go.

With f = (−), z = 0:

fold_left:   ((0 − 3) − 1) − 4  =  −8
fold_right:  3 − (1 − (4 − 0))  =  6

Two results: subtraction does care.

The order of applying f is part of the meaning — unless f is associative. Session 9 makes that the condition for running a fold in parallel.

Algorithm = Logic + Control (Kowalski, 1979), read off the code: f and z are the logic, fold_left or fold_right the control. With + the control changes only the cost; with − it changes the answer.

Kowalski's claim that control "only affects efficiency" holds exactly when the logic is order-independent — associative here. The next slide shows both orders as one picture.

fold as a rewriting of the list’s tree

A list is a tree of (:) nodes ending in []. fold_right f z replaces every (:) by a call to f and [] by z — same shape; fold_left f z builds the mirrored tree from z upwards.

Run fold_left: the accumulator travels left to right, one value carried, every f runs as soon as its element is met — the loop of slide 17. Switch to fold_right: every f must wait for the rest of the list — the "?" nodes are the pending frames of slide 13; then the values come back from the right. Switch to (−): same picture, different answers, −8 and 6.

The same loop in four languages

languagethe sum of a listand its friends
OCamlList.fold_left (+) 0 xsList.map, List.filter
Pythonfunctools.reduce(operator.add, xs, 0)map, filter, comprehensions
JavaScriptxs.reduce((acc, x) => acc + x, 0).map, .filter
Javaxs.stream().reduce(0, Integer::sum).map, .filter

map applies a function to every element; filter keeps the elements a function accepts. Both are folds.

Session 5: who drives this loop — the collection or the caller — and what else a loop can be.

Every language in the room has the loop as a value; the names differ, the idea is one. Python's reduce was moved into functools by Guido, who prefers the explicit loop; that is a taste, not a paradigm.
PART 4

Evaluation order and parameter passing

In which order, and when, are arguments evaluated?

The order of arguments is not part in the program

let f a b = a + b;;
f (print_string "first "; 10)
  (print_string "second "; 20);;
second first - : int = 30

OCaml: right to left — and the manual says unspecified.

JavaScript: left to right, by the standard. C: unspecified.

Never the program. Fixed by the language definition (Java, C#, JavaScript, Python: left to right), left unspecified (C, Scheme, OCaml — right to left in practice), or no order at all (Haskell: an argument is evaluated when used).
The visible symptom of the whole session: with effects, the strategy shows. OCaml's right-to-left is an implementation accident (arguments are pushed right to left); a program that depends on it is wrong by the manual.

Parameter passing: when is an argument evaluated?

A second question, different from the order: whether an argument is evaluated before the call at all.

modethe argument is evaluatedlanguages
call by valuebefore the call, onceC, Java, Python, JavaScript, OCaml, Scheme
call by nameat each use; never if unusedAlgol 60 (its default); Scala, parameters written x: => T
call by needat first use, once; never if unusedHaskell (everywhere); R (every argument is a promise); Scala lazy val
Both questions — in which order, and when — are answered by the language, not by the program. Block 2 derives the three modes from the calculus.
The course table calls these parameter-passing modes. R is the example most students have used without knowing: an argument is a promise, forced on first use, which is why missing() and substitute() exist. Algol 60's by-name is Jensen's device. Scala has both by-name parameters and by-need values. Block 2 slide "The language names" gives the same three rows as reduction orders.

Can if be a function?

A test of call by value: write if as an ordinary function.

let my_if c t e = if c then t else e

let rec fact n =
  my_if (n = 0) 1 (n * fact (n - 1))
Stack overflow during evaluation
(looping recursion?).

Under call-by-value the arguments are evaluated before the call — fact (n - 1) too, even when n = 0, which recurses forever. In such a language if cannot be an ordinary function: it must not evaluate its branches before choosing. So if is a keyword.

Unless the caller keeps the branches from being evaluated — next slide. Or the language decides otherwise — block 2.
JavaScript's RangeError is the same stack overflow. This is the block's open question; do not answer it. Block 2: under call-by-name, if is a function; under call-by-value, it is a function of two thunks — the S4 / S5 split.

Can if be a function? — with the branches as functions

let my_if c t e = if c then t () else e ()

let rec fact n =
  my_if (n = 0)
    (fun () -> 1)
    (fun () -> n * fact (n - 1))
- : int = 120

A function's body is not evaluated until the function is called. Each branch is now a function of no argument; my_if calls only the one it chose, and the other is never run.

So if can be a function — if the caller delays the branches by hand. Block 2 gives this a name, and shows the language doing it instead.
Recorded: demos/my_if2.ml prints 120. Do not say "thunk" or "lazy" yet: the only fact used is that a function body runs when the function is called. Block 2, slide "if as a function under call-by-value", names the wrapping a thunk and puts it on the S5 row of the table; slide 42 shows Haskell doing it in the language.

Conclusion of block 1

the questionthe answer
1What is computing?Two definitions, 1936. In the machine the next step is a function of the state; in the calculus it is a relation, and a strategy makes it a function.
2What does a machine need to call a function?A frame. The stack holds what the calculus keeps in the term. Every loop can be written as a tail-recursive function, every recursion as a loop with a stack.
3Do we need a loop construct at all?No. The recursion is written once, in fold; a use passes the body and writes no control. fold_left and fold_right differ in the order of applying f.
4In which order, and when, are arguments evaluated?The language decides both: the order (fixed or unspecified) and the mode — by value, by name, by need. Under call by value if cannot be a function unless the caller delays the branches.
Each time the choice was implicit, it was in fact the functional paradigm: recursion rather than an explicit stack, fold rather than a loop, a function that delays rather than an argument evaluated first. Block 2 formalises these choices in a minimal setting of the functional paradigm: the λ-calculus.
One line per part; the questions are the dividers' subtitles. If asked whether "machine vs calculus" and "explicit vs implicit control" are the same distinction: they are not — the tail-recursive sum is functional syntax with fully explicit control, and Algol's call-by-name is implicit control in an imperative language.
