    PART 7

    Actors and mailboxes: asynchronous sends into a mailbox in arrival order

    Hewitt 1973, Agha 1985, Erlang; the second family of message passing

    The origins of arrival order in a queue

    Arrival order in a queue, the third resolution of part 4, is the one the RC 4000 gave for requests: senders put messages into one mailbox, and the order of arrival determines which is served first.

    Actors, 1973. The actor model began in artificial intelligence, not in operating systems: Hewitt, Bishop and Steiger 1973, out of Hewitt's earlier work on Planner; as far as is known, independently of the RC 4000.

    Computation as a society of agents: “The model becomes a cooperating society of ‘little men’ each of whom can address others with whom it is acquainted” (page 236); “Every actor should act for himself or delegate the responsibility” (page 238).

    Erlang, 1986. After the RC 4000 and the actors, Erlang reached the same answer at Ericsson, for another reason: fault tolerance.

    Agha's actor primitives in OCaml

    OCaml 5
    toy_actor.mltype msg = Int of int | Ask of actor
and actor = { mutable behaviour : msg -> unit }

let mailroom : (actor * msg) Queue.t =
  Queue.create ()
let create b = { behaviour = b }
let send a m = Queue.push (a, m) mailroom
let become a b = a.behaviour <- b

let run () =
  while not (Queue.is_empty mailroom) do
    let (a, m) = Queue.pop mailroom in
    a.behaviour m
  done

    Agha 1985 gave actors the form in which they are taught today (De Koster et al. 2016, page 33): three primitives, here as a toy in OCaml.

    create makes an actor from a behaviour and returns its address.

    send sends asynchronously to an address and returns at once: the toy pushes the pair onto the mailroom and never waits.

    become replaces the behaviour, so the next message is handled by the new one.

    run takes one pending message at a time and calls its actor's behaviour on it: one turn, run to completion.

    The counter actor and the toy's mailroom

    OCaml 5
    toy_actor.mllet rec counter n self = function
  | Int k -> become self (counter (n + k) self)
  | Ask reply -> send reply (Int n)
    $ ocamlfind ocamlopt toy_actor.ml -o toy_actor
$ ./toy_actor
5

    On Int k, the counter becomes a counter at n + k. On Ask reply, it sends its count to the address given. Two increments and an Ask print 5.

    A send only enqueues. The sender continues at once; the message waits in the mailroom until run takes it.

    Each delivery runs to completion, the Isolated Turn Principle of De Koster et al. 2016: within one turn there is no low-level data race and no deadlock (pages 33 to 34).

    The counter has no mutable variable of its own. Its state lives in the behaviour it becomes next.

    Arrival order. The toy takes the front, Queue.pop: one order only. The model's order is arbitrary; a random pick among the pending messages models it.

    Actors compared with worker pools, objects and Erlang's processes

    An actor has its own identity, its own address and private state, and a mailbox of its own. Two familiar pictures misrepresent this, and both are wrong.

    Not a worker pool, interchangeable labour pulling work from a common pile: an actor is closer to a person with a mailbox of their own. In the kitchen, each cook has an order spike of their own, the ticket is pinned on that cook's spike, and only that cook reads it, in the order the tickets were pinned.

    Not an object. An actor resembles an object that can be written to but never called: nothing returns, and a sender that needs an answer puts its own address in the message.

    Classic actor and Erlang process. A classic actor is a handler that the runtime calls once per message; an Erlang process is a loop that blocks in receive (De Koster et al. 2016, pages 33, 35).

    The guarantees of actor theory and their limits

    Guaranteed

    • every message sent is eventually delivered, after an arbitrary but finite delay (Agha 1985, page 23);
    • a message arrives whole, an aim the model states rather than a guarantee it proves (page 20);
    • one turn is isolated: no low-level race or deadlock inside it (De Koster et al. 2016, pages 33–34);
    • a message is received only after it is sent (causality; Armstrong 2003, page 26);
    • an actor sends to the actors it is acquainted with (Hewitt 1973, page 236, as a metaphor).

    Not guaranteed

    • arrival order, which is arbitrary (Agha 1985, page 22);
    • a bound on the delay;
    • a reply;
    • that a delivered message is "meaningfully processed" (pages 23 to 24);
    • freedom from races and deadlocks across several messages (De Koster et al. 2016, page 34).
    appendixdelivery in TCP and in the actor model, and Agha's infinite stack

    Agha's and Armstrong's arguments for asynchronous sends

    Agha 1985 (pages 19 to 22): “Intuitively, there can be no action at a distance.” A sender can only know a receiver is ready by first sending it something, so synchronous communication is always built on asynchronous communication.

    Armstrong 2003, from fault isolation: “If process communication is synchronous then a software error in the receiver of a message could indefinitely block the sender of the message destroying the property of isolation” (page 23).

    Delivery is then not guaranteed, across nodes or to a dead process; Armstrong calls the result “send and pray” (page 25).

    Message order per pair of processes

    Erlang adds back one guarantee, as “a design decision”: messages between a given pair of processes arrive in the order sent, for ordinary messages in the default mailbox (Armstrong 2003, page 25).

    A's two messages arrive in the order A sent them, and B's in the order B sent them.

    Across different senders Erlang guarantees no order: how their messages interleave depends on the scheduling.

    The lost update and its repair, message by message

    The counter process holds N = 0; two clients will each read it and write it back plus one.

    Both clients send get; the two requests wait in the counter's mailbox in arrival order, client 1's first in this run.

    The counter takes client 1's get and answers 0.

    It takes client 2's get and answers 0 too: neither client has written yet.

    Both clients send set 1, the value read plus one.

    The counter takes the first set: N = 1.

    It takes the second set: N = 1 again, after two increments.

    The repair makes the increment one message: each client sends incr.

    The counter's own sequential code applies both: N = 1, then 2.

    The counter's own code is sequential; the race lies in the order in which its mailbox merges the two clients' messages.

    A request and its reply in the RC 4000, Go and Erlang

    One client and one server in each system, nothing sent yet; the client's queue and mailbox already hold a message from some other process, x and {log}.

    RC 4000: the request travels in buffer b7.

    The answer comes back in the same buffer, into the client's queue behind x; wait answer(b7) takes it by its identity.

    Go: the request carries a fresh channel, reply.

    The server sends the answer on that channel, which, by convention, only the client reads.

    Erlang: the request carries a fresh reference, Ref.

    The answer comes back into the client's mailbox beside other messages, tagged with Ref, and the receive's pattern picks it out.

    The client takes its reply past the other message, by its identity, and who checks that identity: in the RC 4000 the nucleus; in Go the program, by convention; in Erlang the client's own pattern.

    The data carried by a message

    What a message carries also differs between the systems: one sender, one receiver and one send, in three languages.

    Erlang copies the data of a message, except reference-counted binaries and literals, which are shared on one node (the efficiency guide, "Processes").

    A Go channel passes the value it is given, so a sent pointer stays shared.

    Rust moves ownership with the send for a value that is not Copy; a Copy value is copied, and an Arc moves a handle to data that stays shared (the Rust book, 16.2 and 16.3; std::sync::Arc).

    PART 8

    Fairness: eventual choice and eventual delivery

    CSP (1978), actor theory and Erlang's manual

    Fairness in CSP and in actor theory

    Fairness concerns whether a ready communication eventually happens: a question of choice in CSP, which has no messages in transit, and of delivery in actor theory.

    Hoare's example. X sends stop() while Y loops, either receiving the stop or incrementing a counter.

    An unfair implementation. An implementation that always prefers the counter passes X over forever.

    Hoare's refusal. The language does not forbid that, because the implementation would then have to complete programs with unbounded nondeterminism; so “a proof of correctness must not rely on this property” (Hoare, 1978, page 676).

    Clinger's example. In actor theory, the guarantee of eventual delivery is a fairness assumption: a counter increments until a “stop” message arrives.

    Unbounded nondeterminism. The stop is guaranteed to arrive, so the counter always halts, but at any number at all: a program certain to terminate, with infinitely many possible results.

    PART 9

    The delivery assumption: the boundary with session 9

    Delivery on one node, a death reported where requested, and what session 9 changes

    The delivery assumption

    Delivery on one node. This session assumes delivery between the processes of one node.

    Arrival. Every message sent to a live process reaches its queue.

    The one exception. A message sent through an inactive alias is dropped before the queue.

    Handling. Whether the process handles the message is its own doing.

    A death reported where requested. The runtime reports a death exactly where the program requests the report: an Erlang monitor turns it into a DOWN message (the module erlang, monitor/2); the RC 4000’s nucleus returned a dummy answer (Brinch Hansen, 1970, pages 239 to 240).

    A plain send. A plain send to a dead process reports nothing.

    A teaching assumption. The RC 4000’s paper states it for a live receiver on one machine (Brinch Hansen, 1970); neither Erlang’s manual nor Go’s specification states it as such.

    The cost of message passing, and the relation between channels and actors

    the bug study of six Go systems; sharing let back in; the π-calculus and its two limits; channels against actors

    The bug study of Tu, Liu, Song and Zhang

    Tu, Liu, Song and Zhang studied 171 concurrency bugs in six Go systems (ASPLOS 2019).

    "Contrary to the common belief that message passing is less error-prone", more blocking bugs came from message passing (page 6).

    The study's other half points the other way: far fewer non-blocking bugs came from message passing (pages 10 to 11).

    Read together, in the systems studied, message-passing bugs were mostly blocking and shared-memory bugs mostly non-blocking.

    Consistency with the storyThe price of removing sharing is waiting.
    Uses of each primitive (§3.2)Shared-memory primitives are used more often, so by the study's count message passing is even likelier to cause a blocking bug.
    Open questionWhether message passing creates or prevents bugs overall.

    Mutual encodings of channels and actors and their limits

    In Milner, Parrow and Walker's π-calculus (1992), channel names are values that can themselves be sent on channels.

    An actor's address is a channel with exactly one reader, the survey's port (Andrews and Schneider 1983, page 26).

    A channel can in turn be written as an actor that holds a queue.

    In the calculi studied, each family can be translated into the other (asynchronous channels without choice, in Fowler, Lindley and Wadler 2017), with what a translation preserves depending on it.

    Mixed choice, a choice that waits on a send and a receive at once, has no uniform encoding in the asynchronous π-calculus (Palamidessi 1997); a choice among inputs only can be encoded (Nestmann and Pierce 1996), and Go's select offers mixed choice.

    No fairness assumption is carried across by the translations studied: Go's channels guarantee no eventual delivery, actor theory assumes it (Agha 1985), so fairness has to be assumed on each side separately.

    Summary of block 2

    Message passing does not abolish the scheduler: it confines the scheduler's choices that can reach the results to the meeting points.

    This holds as long as processes share nothing by any other route, messages carry values, the runtime delivers them as part 9 assumes, and no process is nondeterminate inside itself.

    Kahn's networks show what happens if no meeting point is ever contested.

    CSP and Go let the programmer write the contest down.

    The RC 4000, actors and Erlang let the system settle it by merging.

    On one node, in every runtime of this story, and in any runtime whose processes share one address space, the shared memory is still there, hidden in one trusted place.

    The cost is paid in waiting, and in races between messages, which the protocol must rule out.

    The RC 4000 process, the classic actor and the Erlang process

    An RC 4000 process is a thread in a loop beside its mailbox: wait, handle, wait again.

    A classic actor inverts that structure: no loop, never waits; a handler that the runtime calls once per message, and become records the behaviour for the next message. Classic actors are therefore event handlers, a state machine written by hand, which is why programming with them resembles asynchronous programming.

    An Erlang process restores the loop: it loops, blocks in receive, and passes its state through recursion. That is the split between Classic Actors and the Processes family (De Koster et al. 2016, pages 33, 35).

    Agha's argument for asynchronous communication

    Where part 5 gave the reasons for the handshake, Agha 1985 argues the opposite (pages 19 to 22). “Intuitively, there can be no action at a distance.” A sender can only know a receiver is ready by first sending it something, so synchronous communication is always built on asynchronous communication.

    Without buffering, an actor cannot send a message to itself, and recursive computation requires that.

    A fast sender, a typist faster than an editor, should not be held to one character at a time.

    back

    Armstrong's argument from fault isolation and its gaps

    Erlang, developed at Ericsson from 1986 with first experiments in 1987, arrived by an independent route at semantics like the actor model's: a design convergence, not a derivation from actor theory, with fault tolerance as its motive. Armstrong 2003 sets out the argument.

    1. The essential problem in a fault-tolerant system is fault isolation: errors in a faulty module must not reach a correct one (page 17).

    2. Any shared resource lets an error in one process corrupt it, so processes share nothing (pages 19, 23).

    3. Message passing must be asynchronous: “If process communication is synchronous then a software error in the receiver of a message could indefinitely block the sender of the message destroying the property of isolation” (page 23).

    4. Delivery is not guaranteed, across nodes or to a dead process; the sender can learn that a message arrived only from a confirmation sent back (pages 22–23).

    Armstrong calls the result “send and pray” (page 25).

    No timeout. Step 3 assumes a synchronous send with no timeout, which a timed send would bound.

    One shared resource left. An unbounded mailbox leaves the node's memory, which a stuck receiver's mailbox can exhaust for every process. Armstrong concedes a version of this himself, for operating-system processes that share one CPU and one memory, calling isolation “only true to a first approximation” (page 17).

    Sending order, arrival order and receiving order

    One process sends itself first, second and {urgent, 3}.

    Go's select and eventual service

    The rule of the specification. Each time a select runs, one of its ready cases is chosen by uniform pseudo-random selection (the Go specification, “Select statements”).

    An inference, with probability 1. A case that stays ready is taken eventually, if the choices are independent and the goroutine runs the select again and again while the case stays ready.

    Not stated by the specification. Eventual service of a ready case, and any order among blocked senders on one channel.
