Block 1. Mutual Exclusion

Which ways control the interleavings of a multi-threaded program, and what does each guarantee, require and risk?

PART 1

Threads and shared memory

the scheduler, interleavings, sequential consistency

Threads, memory and the scheduler

Thread. A sequence of instructions that the processor executes one after another, with its own position in them and its own local variables.

Instruction. One step the processor executes as a whole: a read of one memory location into the processor, a write of one value to one location, an operation inside the processor.

A line of source code is usually several instructions: n++ is a read, an addition and a write.

Shared memory. Locations that every thread can read and write by their address: fields and array elements, not the local variables of a Java method.

Scheduler. Decides which thread runs where; may stop a thread between any two instructions and resume it later.

Its parts: a queue of the threads ready to run; a policy that picks the next one; a timer interrupt that stops the running thread; a context switch that saves its registers and program counter and loads another's.

The interleaving

Definition. An execution of a multi-threaded program is an interleaving of its threads' instructions: one sequence that contains every instruction of every thread, each thread's instructions in the order the thread issues them.

Two threads of m and n instructions have \(\tbinom{m+n}{n} = \tfrac{(m+n)!}{m!\,n!}\) interleavings: an interleaving is fixed by the n positions of the second thread among the m + n. Here \(\tbinom{6}{3} = 20\); for the counter's two loops of \(3\cdot 10^6\) steps, \(\tbinom{6\cdot 10^6}{3\cdot 10^6} > 10^{1\,800\,000}\).

Two threads that each execute a million three-step increments have more interleavings than any test could run.

! A correctness argument does not look at runs. It should cover every interleaving at once;
that is what the rest of this block does.

Four assumptions

  1. Several threads. Two or more, each a sequence of instructions.
  2. One shared memory. All threads read and write the same locations.
  3. A scheduler that may stop a thread between any two instructions. So an execution is an interleaving, and any interleaving may occur.
  4. Sequential consistency. There is one memory, and every read returns the value of the latest write to the same location before it in the interleaving; with assumption 3, this is Lamport's sequential consistency*.Each processor buffers its writes and compilers reorder, so this is not literally what the hardware does: a guarantee of the language, given only for programs without data races, defined in part 2.

* L. Lamport, IEEE Transactions on Computers C-28(9), September 1979, pages 690–691: the definition.

Data race

Data race. Two accesses to one memory location from two threads, at least one a write, with nothing of the program ordering one before the other.*

To avoid the race, the two threads must coordinate: what can the program put between the two accesses?

* The Java Language Specification, 17.4.5; C++, Rust and OCaml state the same; Java and Go, in their own terms.

Synchronization mechanisms

Synchronization. The order a program can impose; three mechanisms give it.

A lock. Its release is ordered before the acquire that follows it: what the releasing thread wrote before, the thread that acquires next sees after.

A thread's start and join. The call of start is ordered before the new thread's first instruction, and its last instruction before the return of the join that waits for it.

An atomic. A write to an atomic or volatile variable is ordered before the read that sees it, with everything the writer did before.

Each mechanism orders one thread's instructions before another's: what the first thread wrote before, the second sees after. The counter has none of them between its accesses, and that is its data race.

But is a data race the only fault in the counter?

Atomicity violation

Atomicity violation. An operation of several steps meant as a unit, atomic, every other thread seeing all of it or none, and not protected as a unit, so that another thread's step can fall between two of its steps.

The counter is both.

In part 6's transfer each access is under its lock: no data race, and still an atomicity violation.

PART 3

Atomic instructions

test-and-set and spin locks

Naive lockTest-and-set and its guarantees

A naive lock. To acquire, a thread reads the flag and, if it is false, writes true. Two steps on a shared location: the other thread can read between them, and both threads enter.

The lock protects the critical section; but then what protects the lock itself?

Test-and-set. An instruction that reads the old value of one memory location and writes a new value to it as one indivisible step: no instruction of any other thread falls between the read and the write.

Indivisibility. It reads the old value and writes the new one as one step: no thread sees the location between.

Synchronization. The write of false that releases the flag is ordered before the test-and-set that reads it, and with it everything the releasing thread did before.

Spin lock. A flag, a boolean location, and a loop: to acquire, a thread repeats test-and-set on the flag until the old value is false, spinning while it finds true; to release, it writes false.

The first guarantee makes the lock exclusive; the second makes the plain variable inside it race-free.

A waiting thread is suspended until the release, not spinning; the closing brace releases the lock even on an exception.

Lock. An object with two operations, acquire and release: between a thread's acquire that returned and its release, no other thread's acquire returns.

Critical section. The instructions a thread executes while holding the lock.

The contract and the obligation

Contract. Operations are atomic by exclusion: under the lock they happen one after another, and each appears to the other threads to happen at one instant inside its critical section.

Obligation, two parts here. Every access to the protected state, read or write, while holding the lock; and the lock held for the whole operation, over every piece of state its invariant mentions, the statement that holds whenever no thread is inside a critical section.

A lock protects only against the threads that take it: a new lock per call, synchronized (new Object()) { n++; }, is held by one thread and never taken by another. The lock that works is one lock shared by every thread that touches n.
The obligation is then the programmer's discipline: the lock enforces none of it.

The progress risk of a lock

Progress risk, first source: a stopped holder. A thread that holds a lock and is stopped stops every thread that needs it. Stopped in a cycle, it is deadlock; not scheduled, a missed deadline, in the appendix.

Second source: starvation. A lock that keeps changing hands may never reach one thread. An order among the waiters removes it, and block 2's wait-freedom rules it out.

Spinning: the spin lockSuspended: the language's lock
A waiter costsa busy processor, for as long as it waitsno processor time; waking it up costs a switch of threads
A stopped holderthe waiters spin as long as it is stopped; on one processor, a spinner takes the time the holder needs to finishthe waiters leave the processor to the holder, and still wait as long as it is stopped
A lock changing handsno order among the waiters: starvationa woken waiter competes with newcomers: starvation

Suspension saves processor time; it removes neither source of the risk. Only an order among the waiters removes starvation: a ticket lock spins in turn, a fair lock suspends in turn.

And who checks that every access is under the lock -- programmer's discipline or can a language enforce it ?

Deadlock. A state in which every thread of a set waits for a lock held by another thread of the set, so that none of them can ever proceed.

$ java Accounts b
deadlock: 2 threads blocked for ever
  t1 holds account A,
     waits for account B, held by t2
  t2 holds account B,
     waits for account A, held by t1

Safety and liveness

Safety property. Something bad never happens; a violation is a finite run, one that reaches the bad state. Liveness property. Something good eventually happens; no finite run can show a violation, since the good thing may still come.*

The deadlock violates both kinds. That each thread holds one lock and waits for the other's is a state, and the detector finds it: "never deadlocked" is a safety property. That no transfer will ever complete is the liveness property it ruins; no detector can see "ever".

* Lamport 1977 (IEEE TSE SE-3(2), 125–143); Alpern and Schneider 1985 (Inf. Proc. Letters 21(4), 181–185).

The Coffman conditions (1971)

Four conditions are all necessary for a deadlock:

  1. Mutual exclusion. A resource is held by one thread at a time.
  2. Hold and wait. A thread holds a resource while it waits for another.
  3. No preemption. A held resource cannot be taken away.
  4. Circular wait. A cycle of threads, each waiting for a resource the next holds.

This session removes the fourth.

Every thread that takes several locks takes them in the same order. A thread waits only for a lock later in the order than every lock it holds; along a chain of waiting threads the locks come later and later, and a chain that only goes up cannot return to its start.

The order is the third part of the obligation. No compiler checks it, and the deadlock compiles in safe Rust; tools find it only in runs.

A lock makes a thread wait, spinning or suspended, for its turn. But a consumer that finds a buffer empty must wait until the buffer holds an item: what does a thread use to wait until a condition on the shared state holds?

PART 7

Summary

mutual exclusion: guarantee, obligation, progress risk

Mutual exclusion in summary

The guaranteeOperations atomic by exclusion: under the lock they happen one after another, each at one instant inside its critical section.
The obligationEvery access to the protected state under the lock; every lock the invariant needs, held for the whole operation; one global order of the locks.
The progress riskA stopped holder stops every thread that needs its lock: deadlock when the holders wait in a cycle, a missed deadline when the holder is not scheduled. And starvation, when the lock keeps changing hands but one thread is passed over for ever.
Who checksNobody by default, in Java, OCaml 5, Go, C and C++; a detector at run time, with Go's -race or ThreadSanitizer, for the accesses a run made; Rust's compiler, for data races only, never the lock order or atomicity.

The question for block 2

The counter has been exact twice, under the spin lock and under the language's lock, both by exclusion. The spin lock was built from one instruction that is itself atomic, test-and-set.

Then can an operation be atomic without a lock around it?

Block 2 answers three questions this block leaves open: what an atomic operation without a lock guarantees and requires; how to prove such an operation correct; and, at its end, what the language guaranteed about memory in the fourth assumption, and what holds instead for a program with a data race.

APPENDIX

Bounds and priority inversion

the bounds on the printed value; Mars Pathfinder and priority inheritance

The bounds on the printed value

At most 2N: every write stores one more than a value read.

Exactly 2N is possible: in every interleaving in which no two increments overlap, that is, no read of n falls between another increment's read and its write.

At least 2, for every N of at least two.

back

Mars Pathfinder (1997)

In July 1997, days after landing, Mars Pathfinder's computer began to reset itself, each reset stopping the day's work (Reeves, 1997).

The cause was a priority inversion: a high-priority task waited for a lock held by a low-priority task, which medium-priority tasks kept from running.

The lock did its job: one task at a time held it. What failed was progress: the high-priority task missed a hard deadline, and the system reset. Not a deadlock: one lock, no cycle. An unbounded priority inversion: the holder was ready to run, and the scheduler kept choosing the medium tasks.

back

Priority inheritance and the priority ceiling

The remedy was priority inheritance: a task holding a lock runs at the priority of the highest task waiting for it. JPL turned it on by a patch sent from Earth.

Inheritance alone does not prevent deadlock on two locks taken in opposite order; a fixed order does, anywhere, and on one processor so does the priority ceiling protocol (Sha, Rajkumar and Lehoczky, 1990).

APPENDIX

Condition synchronization

semaphores, monitors and condition variables

Dijkstra's bounded buffer (1965)

Semaphore. A counter with two indivisible operations: P waits until the counter is above zero and then decreases it by one; V increases it by one. In the Part 2 introduction and in Java's library: acquire and release.*

Three semaphores around a queue of N places:

  • number of empty positions, starting at N
  • number of queuing portions, starting at 0
  • buffer manipulation, starting at 1

The one that starts at 1 is a lock: its P is acquire, its V is release, at most one process between them.

The two that count are waiting devices: a P on a counter at zero makes the producer wait for a free place, or the consumer for a portion, until the other's V.

* Dijkstra, Cooperating sequential processes, EWD 123, 1965, section 4.3.

back

The monitor

Monitor. A module that packages some shared state, one lock that every operation on the state holds, and condition variables.*

Java: every object is a monitor; a synchronized method holds its lock, wait() and notifyAll() are its one condition variable. OCaml 5: a record with a Mutex.t and one Condition.t per thing to wait for.

* Brinch Hansen, Operating System Principles, 1973; Hoare, Communications of the ACM 17(10), 1974.

    throws InterruptedException {
  while (count == 0) wait();   // empty
  Integer x = slots[head]; slots[head] = null;
  head = (head + 1) % K; count--;
  notifyAll();
  return x;
}

Example 5 with if

The same buffer with if (count == 0) wait(); in place of the while, and likewise in put. Two producers, two consumers. What changes?

  1. Nothing: a consumer is woken only when an item has been put.
  2. A consumer woken by a put finds the buffer empty again, the other consumer having taken the item first, and takes from an empty buffer.
  3. Both consumers wait for ever.
  4. A consumer takes the same item twice.

Mesa's monitors and Hoare's

Hoare's monitors (1974) hand the lock over to the woken thread at once, at the signal.

Mesa's monitors (Lampson and Redell, 1980) hand the lock back later, when it is free; Java's and OCaml's condition waits are Mesa's.

So the condition is checked again, in a while.

wait may return with no notify at all, a spurious wake-up, which Java and OCaml allow.

The obligation's fourth part: every wait in a loop that checks its condition again. And notifyAll rather than notify: an object has one waiting set, and waking one thread may wake one of the wrong kind.
