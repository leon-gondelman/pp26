The question

What is a datatype?

Some answers we would all give:

  • int32 — the same, but exactly \(2^{32}\) of them?
  • struct — several values glued together?
  • class — values with code attached?
  • “a collection of values” — of what, arranged how?

What is an algebraic data type?

Last week we read two of them without the name — and used the first in the type of pop:

Every value is built from a closed list of shapes, and taken apart the same way.

PART 2

Two ways to be a set

The discovery, in JavaScript
No OCaml, no Java, no classes: arrays and arrow functions only. The room already reads this.

One interface

A set of integers. Four operations, and nothing else:

empty              // the set with no elements
insert(s, n)       // the set s, with n added
contains(s, x)     // is x in s?
union(s, t)        // every element of s, or of t

Client code uses only these four names.

Two implementations follow. The client cannot tell them apart. At least at first.

Cook 2009's running example. Keep the interface small: four names, one of them binary.

Way 1 — a set is data

Every operation inspects* the array.

union1 inspects both of its arguments.

* inspect: read the representation directly — here as an array; in OCaml, as a constructor and its arguments.

Say "inspects" every time; Way 2's verb is "calls". The pair of verbs is the whole duality. The spread [...s, n] copies and extends: persistent like :: in S2, but O(n).

Way 2 — a set is a function

A set is a function that answers one question: is x inside?

Every operation calls* the set. contains2 is just the call.

* call: use a value only through the interface it exposes, learning nothing about how it is made.

union2 can do nothing with s and t except call them. There is no inside.

insert2 returns a NEW function — the parentheses show it: "x is in the new set if it is n, or if the old set says so". Read it aloud once. The next slide unfolds two inserts.

Two inserts, unfolded

Way 1

const s3  = insert1(empty1, 3)
       // = [3]
const s35 = insert1(s3, 5)
       // = [3, 5]

Each step produces data: an array anyone may inspect.

Way 2

const s3  = insert2(empty2, 3)
       // = x => x === 3 || empty2(x)
const s35 = insert2(s3, 5)
       // = y => y === 5 || s3(y)

Each step produces a closure*. s35 holds s3; nothing runs until someone calls it.

* closure: a function together with the bindings it captured where it was defined — here n and the previous set.

Both s35 are chains of length two: [3, 5], and a function holding 5 and s3, which holds 3 and empty2. Same shape — and, from the operations’ side, one can be inspected while the other can only be called.
This is the closure made concrete: n and s live on inside the returned function. The "same shape" remark is the seed of slide 18 (set as a recursive type): Insert (5, Insert (3, Empty)) is the same chain, written as data.

Inspects both. Could sort, merge, deduplicate, compare.

Way 1: an operation on two sets sees both representations — it can merge them, or compare them.
Way 2: it can only ask each set about an x and combine the answers. The two sets themselves are never compared.
This is the binary-method row of Cook's table, and function extensionality, without either name. Identity as a substitute for equality comes in S7.

Two ways, stated

Way 1 — a set is dataWay 2 — a set is a function
a new operationone new functionevery set rebuilt
a new kind of setevery operation changedone new function
an operation on two setsinspect bothcall both — no comparison
Way 1: a value is one of a closed collection of representations, open to every operation. A new operation is free; a new representation affects every operation.
Way 2: a value is its own operations, bundled together when it is made. A new implementation is free; a new operation affects every implementation.

Two ways of implementing one interface. Neither is a language feature — we used arrays and arrow functions. The names come next.

Layer 1, stated. Do not name ADTs or objects yet; that is the next divider. If asked about deletion: remove is one line on both sides — remove1 = (s, n) => s.filter(x => x !== n); remove2 = (s, n) => x => x !== n && s(x). Way 2 handles every POINTWISE operation (union, intersection, difference, remove, and complement x => !s(x), which Way 1's arrays cannot represent at all). What Way 2 cannot do is observe the set as a whole: size, isEmpty, enumerate, equal. The boundary is pointwise-through-the-interface vs requires-inspecting-the-whole.
PART 3

Algebraic data types

Way 1, made precise

Naming the two ways

what we builtwhat it is called
Way 1 — a value is data; operations inspect italgebraic data types
Way 2 — a value is a function; operations call itobjects

Both are older than the languages we write them in. Reynolds (1975) called them user-defined types and procedural data structures — “complementary approaches to data abstraction”.

Two ADTs, one acronym.
Abstract data type (Liskov & Zilles, 1974): a type its clients know only through its operations — session 11.
Algebraic data type (Hope, 1980): a type whose values come in a closed list of shapes — today.
The acronym clash costs students hours. Say it once, clearly. The abstract one is Way 1 with a wall in front; the wall is S11.

An enumeration

type note = C | D | E | F | G | A | B

let semitones n = match n with
  | C -> 0 | D -> 2 | E -> 4 | F -> 5 | G -> 7 | A -> 9 | B -> 11

Reading rule: | is or. A note is C, or D, or …

The constructors are values we invent. C is not 0; nothing is inside it. It is a tag, as kind: 'evens' was for the set — but one of exactly seven values of a new type, note, each distinct from the others by construction.

The usual encoding in C, and in Java before enum, was static final int C = 0, D = 2, …
Now C + D compiles, and 7 is accepted wherever a note is expected. A variant type allows neither.
The leap students miss: a type declaration can create values, not only arrange existing ones. Say it.

Carrying values: products and sums

type pitch    = { note : note; octave : int }
type duration = Whole | Half | Quarter | Eighth
type symbol   = Note of duration * pitch | Rest of duration
  • pitch is a product type: each of its values holds every field.
  • symbol is a sum type: each of its values is exactly one alternative — a Note carrying a duration and a pitch, or a Rest carrying a duration. That is what of reads as.

A Rest carries no pitch: no field is left empty or set to null — a rest with a pitch cannot be written at all.

let beats s = match s with
  | Note (d, _) | Rest d -> beats_of d
The or-pattern binding d in both arms: first sight of a pattern doing work. The lab uses exactly this line.

Why “algebraic”

Count the values of a type

unit\(1\)
bool\(2\)
note\(7\)
duration\(4\)
pitch = note × int\(7 \cdot |\mathrm{int}|\)
symbol = duration × pitch + duration\(4 \cdot 7 \cdot |\mathrm{int}| + 4\)
The type constructors form an algebra. Counting is its simplest model — and it works for infinite types too, as laws rather than numbers.

Products multiply, sums add

\[|A \times B| = |A|\cdot|B| \quad\; |A + B| = |A| + |B|\]

The laws of arithmetic hold as isomorphisms of types, with a conversion function each way:

\[A \times (B + C) \;\cong\; A\times B + A\times C\]

Cardelli and Wegner 1985 for "a type is a set of values"; the isomorphism is the honest content of the word "algebraic". Do not go to generating functions here.

Two encodings of one type

A struct with a tag

struct symbol {
  int tag;        /* 0 = note, 1 = rest */
  int duration, note, octave;
};

\(2^{128}\) states. Most mean nothing: a rest with a pitch; a tag of 7.

A sum

type symbol =
  | Note of duration * pitch
  | Rest of duration
  (* two shapes, nothing else *)

\(4\cdot 7\cdot|\mathrm{int}| + 4\) states. Each means something.

Sums do not add possibilities. They remove meaningless ones.
optionabsence as one explicit case: None | Some of 'a has one more value than 'a, and every match must handle it.
nullabsence added to every type at once and recorded in none: no match is required, but the missing case surfaces at runtime as a NullPointerException.
This is "make illegal states unrepresentable" (Minsky), stated as arithmetic. NullPointerException is an unchecked match.

Recursion: a type mentioned in its own definition

type 'a list = [] | (::) of 'a * 'a list

type set = Empty | Insert of int * set     (* slide 6, as a type *)

let rec contains s x = match s with
  | Empty            -> false
  | Insert (n, rest) -> n = x || contains rest x

Its equation, solved: \(L = 1 + aL \;\Rightarrow\; L = \tfrac{1}{1 - a} = 1 + a + a^2 + a^3 + \cdots\)

A list is empty, or one element, or two, or three … — a tuple of some length, one shape for each length.

The set we wrote as an array on slide 6 is now a type. The closed list of shapes — Empty, Insert — is written down where the compiler can read it.

Recursion is the last rung needed for the lab. Trees are block 2's business (the melody type).

Constructors* are functions — but not ordinary ones

length : 'a list -> int               (* an ordinary function *)
Note   : duration * pitch -> symbol   (* a constructor *)

An ordinary function may lose information: from length xs we cannot recover xs; many lists share one length.

A constructor loses no information. Three properties no ordinary function has:

injectivedifferent arguments give different values
disjointdifferent constructors never build the same value
exhaustiveevery value of the type came from some constructor
So every value was built in exactly one way: one constructor, applied to the values it carries.

* Unlike Java’s constructors, these run no code and can be taken apart: a tag with a payload.

This is the free-algebra property in plain words: no equations between terms. If asked: in OCaml a constructor is not a first-class function — pass (fun x -> Note x); the slide shows the type it behaves as, not a val declaration. Java's nearest relative of an ML constructor is a record; ML's nearest relative of a Java constructor is a smart constructor (a validating function that then applies the real one).

Matching is the inverse

let s = Note (d, p)              (* forwards:  build            *)
match s with Note (d, p) -> …    (* backwards: recover d and p  *)
A constructor goes from the carried values to the value: (d, p) ↦ Note (d, p).
A match goes from the value back to the carried values: Note (d, p) ↦ (d, p).
It can, because every value was built in exactly one way.
  • We cannot match on f x for an arbitrary f: there is no inverse to run.
  • We cannot match on a Way 2 value: any function may have produced it, and nothing in it says which, or from what — its environment is sealed, and there is no fixed list of makers. There is nothing to invert.
  • The list of shapes used to live in a comment. Now it lives in the type, and the compiler reads it: every match covers every shape, and no case is unreachable.
"Documentation became a declaration." This is the bridge to the lineage slide: C's union with a tag is the version where the list was a comment.

Algebraic data types: a timeline

1970sPascal variant records; C union with a tag field — the list of shapes is a convention, unchecked
1980Hope (Burstall, MacQueen, Sannella): algebraic data types with pattern matching
1984 →Standard ML, then OCaml and Haskell: the ML family makes them the default
2014 →Swift enums, Rust enums, Kotlin sealed classes, TypeScript discriminated unions
2021 →Python 3.10 match; Java 17 sealed, Java 21 pattern switch

“Algebraic” also names the mathematics: the values of the type are exactly the terms built from its constructors, nothing more and nothing identified — the initial algebra of its constructors (Goguen, Thatcher, Wagner, Wright, 1977).

The convergence is the lecture's arc: every mainstream language now has Way 1 built in. Keep the last line to one breath.
PART 4

Objects

Way 2, made precise
Same order as part 3: the thing we built, written as a type, then what the type does and does not say. No sealed anywhere in this part; Java doing Way 1 is part 5's evidence.

The set as objects

type set =
  < contains : int -> bool; size : int >

let empty : set = object
  method contains _ = false
  method size = 0
end

let insert (s : set) n : set = object
  method contains x = x = n || s#contains x
  method size = s#size + 1
end

type set is the interface of a set — extension 1’s record of operations, as a type — and under it two kinds of set, empty and insert.

In the Way 1 type they were the constructors Empty and Insert; here the type lists only operations, and the kinds live in the code.

No match on a set: nothing at compile time says how many kinds exist, or which one we hold.
That is the point: which kind we hold is decided at run time, by the object, when it is called — dynamic dispatch.

* object … end builds one object and # calls a method. No class is involved; OCaml does not need one.

Verified: demos/objset.ml prints "true false 2 true". Read insert aloud: the new object holds s and n in its closure, exactly as insert2b did on the JavaScript slide. Sum with payload, not an enum: an enum as classes looks silly and Java has enum anyway.

The same, in Java

abstract class Set {
  abstract boolean contains(int x);
  abstract int size();
}
class Empty extends Set {
  boolean contains(int x) { return false; }
  int size() { return 0; }
}
class Insert extends Set {
  private final Set s; private final int n;
  Insert(Set s, int n)
    { this.s = s; this.n = n; }
  boolean contains(int x)
    { return x == n || s.contains(x); }
  int size() { return s.size() + 1; }
}

The abstract class is the interface*; each subclass is one kind, with its own operations.

The fields are private**: from a client’s side, a Set is only what its methods answer.

* A Java interface says the same, without fields or shared code.
** private: no client reads the field. final: assigned once, in the constructor — a set never changes after it is made.

Verified: demos/Sets.java prints "true false 2". Do not say sealed here. The interface question is answered on this slide only, in the footnote: an interface is the same declaration without fields or shared code; abstract class chosen so that part 5 can say "abstract class + subclasses = Way 2" and "sealed + records + switch = Way 1". final: the S2 point — a persistent value, no mutation after construction.

A new kind, in Java

A new kind is one more class:

class Evens extends Set {
  boolean contains(int x) { return x % 2 == 0; }
  int size()              { return Integer.MAX_VALUE; }
}

Set, Empty, Insert and every client stay as they are:

Set s = new Insert(new Insert(new Empty(), 3), 5);
s.contains(4);

Which contains runs is decided by the object s holds, at run time — three calls down the chain, none visible to the caller.

Dynamic dispatch on the receiver only: s is an Insert, so Insert.contains runs; it calls its inner Insert; that calls Empty.contains, which answers false. Had s been an Evens, the same client line would run Evens.contains. Contrast with Way 1, where the even numbers forced a change in every operation.

Classes

Nothing so far needed a class. In everyday languages, a class bundles several jobs:

  • factory — new makes objects
  • code sharing — methods written once
  • type — Set in signatures
  • privacy boundary
  • inheritance — session 10
  • namespace — Set.empty

Languages disagree on which to bundle, and on whether to have a class at all:

JavaSmalltalkJavaScriptOCamlGo
public boolean equals(Object o) {
  return o instanceof Insert i && i.n == n && i.s.equals(s);
}

All six jobs in one box. Privacy is per class, not per object: equals reads another object’s n. The static methods of a class are the operations of an abstract data type.

s := Insert new.
x > 0 ifTrue: [ 'positive' ] ifFalse: [ 'not' ]

A class is itself an object, and new is a message to it. Even if is a message: ifTrue:ifFalse: is sent to the boolean, and the boolean object decides. Compilers inline it; the meaning is the send.

const empty = { contains: x => false };
const evens = Object.create(empty);
evens.contains = x => x % 2 === 0;

No class underneath: objects are made from objects. A prototype is another object, asked when a property is missing. The class syntax of 2015 writes this down and adds no mechanism.

let empty = object method contains _ = false end
(* empty : < contains : 'a -> bool > *)

An object without a class. Its type is the list of its methods. A class, when we want one, is a recipe for making objects — a factory and code sharing, nothing more.

type Reader interface { Read(p []byte) (int, error) }

No classes and no implements: any value with a Read method is a Reader. The interface is satisfied by shape — session 10. Same way, different amount of declaration.

Java panel verified: demos/Eq.java prints "true false". Fields: from outside, a field read is an operation with no arguments (Meyer's uniform access; Self's slots); public fields leak the representation — a product, Way 1. Dispatch ladder if a student asks how equals could see both: static (no dispatch) / a.equals(b) dispatches on the receiver only — the binary-method problem, Bruce et al. 1995 / visitor dispatches on both, next part / multimethods dispatch on all, S10. C++ (multiple inheritance, classes as structs with layout) is left out: it repeats Java's bundling, and inheritance is S10's axis. PART 5

Abstract data types versus objects

What each hides, and how each grows — Reynolds 1975 · Cook 2009 · Wadler 1998

One abstraction barrier, placed two ways

Both ways hide how an operation works: a client calls contains and gets an answer, never seeing the body — the array scan, or the chain of calls. Any function does this much. What each way adds differs:

[ADT]Way 1, behind a wall we will build in session 11. The representation type is hidden: behind an .mli, as session 2’s stack, type t shows no constructors, so no client can match on a set or build one by hand. Cook calls this type abstraction. Only a compiler can enforce it.
[Objects]Way 2, as it stands. Nothing is hidden at the type level: the interface type is public. What is hidden is the environment of one closure — this s, this n — and it is hidden by being a function: nothing but a call can reach in. Cook calls this procedural abstraction: a procedure’s wall, with the data inside.
One wall around the whole type, or one wall around each value.
Objects need no type system to keep their secrets; abstract data types do.
Cook 2009, "On understanding data abstraction, revisited", section 3. The sharp version: an untyped lambda calculus has objects but cannot have abstract data types. Keep "abstract" and "algebraic" apart on this slide — say the whole word each time. Bullet 1 is the shared part; bullets 2 and 3 are what each way adds on top of it, and they add different things.

Way 1 — sealed, records, switch

sealed interface Shape
  permits Circle, Square, Tri {}

Visitor: pattern matching by hand

interface Visitor<R> {
  R onEmpty();
  R onInsert(Set s, int n);
}
abstract class Set {
  abstract <R> R accept(Visitor<R> v);
}
class Empty extends Set {
  <R> R accept(Visitor<R> v)
    { return v.onEmpty(); }
}
class Insert extends Set {
  <R> R accept(Visitor<R> v)
    { return v.onInsert(s, n); }
}

Way 1 would write one match, an arm per kind. Java has none; we build it by hand:

  • the visitor: one method per kind, onEmpty and onInsert — the arms
  • accept: each kind’s one new method; it calls its own arm and hands over what it carries
  • s.accept(v) dispatches twice: the set picks accept, accept picks the arm. The set chose the arm, not the caller.

Way 1’s trade, cost included: size is one visitor, written outside; a new kind needs onEvens in every visitor.

Empty | Insert of int * set ≅ { on_empty; on_insert }: a sum of products is a product of functions.

Java 21's switch on a sealed type does the same without the ceremony — a design pattern is often a missing language feature, written by hand (Norvig 1996, in plain words). Verified: demos/V.java prints 2 for size via an anonymous visitor; demos/visitor.ml does the same with a record of functions. The ∀r form is S4's Church/Böhm–Berarducci encoding — say "visitor" here, not "Church". The last line is Norvig's observation (1996) in plain words.

What each way is good for

Objects

  • extension by strangers — a framework defines Widget; plug-ins add kinds it never sees
  • state that changes, behind a wall — a counter, a connection: only its own methods touch it (Parnas, 1972)
  • collections sharing only an interface — a list of sets, of any kinds

Algebraic data types

  • closed domains, modelled exactly — messages, UI states, Option
  • programs that process trees — compilers, interpreters, query planners, JSON: few node kinds, many operations, some on two nodes at once
  • code that grows by a kind — the compiler lists every site to fix
  • data that travels — files, the network: only a tag and its payload can go

Much “object” code is data with getters — the shape that record and sealed were added to Java to fix.

Parnas 1972, "On the criteria to be used in decomposing systems into modules": hide the decisions likely to change. Trees: the node kinds are fixed by the language or format; the operations are open-ended and several are binary (equality of types, unification, rewrite rules matching nested patterns) — extension 3 again. Data that travels: serialisation is Way 1 by necessity; an object cannot be sent, only described.
