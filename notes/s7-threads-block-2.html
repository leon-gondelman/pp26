The session names three ways to control the interleavings of a multi-threaded program. The first way, mutual exclusion, forbids the harmful interleavings with a lock; it was block 1's. The second way, the atomic instruction with retry, lets the threads interleave, detects an interleaving that changed what a thread read, and retries. The third way, independence of the order, arranges the work so that no interleaving can change the result. Block 1 ended on a question: can an operation be atomic without a lock around it? This block answers it in three steps. First it states what a client is entitled to ask of an operation that several threads call at once, and what a client is entitled to ask of its progress; those are the standards against which any answer is judged. Then it gives the answer, the second way: one atomic instruction with a loop around it, on the counter and then on a stack, with the proof that the stack meets the standards. Then it takes the third way, where the work is arranged so that its result does not depend on the order. It ends with the fourth assumption that block 1 made about memory: it is a guarantee, and section 7 says who gives it and what a program gets when it breaks the guarantee's condition.

The programs on this page are the session's running examples; each shows the slide's lines, with the declarations and lines that the run needs. Java is the language the lab is written in; OCaml 5 is the lecture's second specimen, and its programs are read beside their Java twins, with the comments. In OCaml 5 a domain is the unit of parallel execution: each domain runs on an operating-system thread of its own, so several domains run in parallel on several cores, whereas the threads of OCaml's Thread library within one domain take turns. Domain.spawn starts a domain and Domain.join waits for it and returns its result, as start and join do in Java. A core is one of the processor's units that each run one thread at a time.

1. Linearizability and progress

An operation without a lock needs its standard stated before it is built: what it has to achieve. The locked stack of block 1 is the reference: it is correct, and block 1 showed why: every push and pop holds the stack's one lock for its whole body. A client of a data structure is the code that calls its operations, here the threads that push and pop. The question of this section is what exactly the lock gives a client, so that a version without the lock can be held to the same standard.

The locked stack, the reference

Example 7a, Java: LockedStack.java, the lines the slide shows

record Node(int value, Node next) { }   // a record: its fields are final, set once

Node top = null;                     // guarded by this stack's lock

synchronized void push(int x) {      // one thread at a time
  top = new Node(x, top);
}
synchronized Integer pop() {         // null when the stack is empty
  if (top == null) return null;
  Node old = top;
  top = old.next();
  return old.value();
}
$ java LockedStack
one lock: pushed sum 125000500000, popped 62500849627 + remaining 62499650373 = 125000500000

The sums agree, which is what a stack that loses no push and pops nothing twice must give; the check catches a lost or doubled value unless two such mistakes cancel, and one run proves nothing in general. The run does not yet say what a client of this stack may rely on in general; saying it takes the definitions that follow. In what follows, a word is one location of memory that the processor reads or writes in one indivisible step; an int fits in a word, and so does a reference, the address of an object in memory.

Histories and linearizability

A concurrent object is a data structure, here a stack, with operations that several threads may call at the same time. A history of an object is the record of one run as seen from outside: for each operation, the thread that called it, which operation it is with its arguments, the instant at which the thread called it, the instant at which the call returned, and the value returned. Two operations overlap in a history when each is called before the other has returned. The sequential specification of the object says what each operation does when operations run one at a time, one after another: for a stack, a pop returns the value of the most recent push among those not yet popped, and returns null when every push has been popped. A sequential run of the specification is a sequence of operations applied one after another, each returning what the specification says it returns; for the stack, a run of the sequential stack.

A history where no two operations overlap is checked against the sequential specification directly: the check runs the operations in the order of their calls and compares the returned values. A history with overlapping operations has no single order of its operations, and that is the difficulty: two pushes that overlap could have gone onto the stack in either order, and a later pop will show which. Herlihy and Wing gave the standard that resolves this difficulty.1

Linearizability. A history is linearizable when two things can be done. First, each of its operations is assigned one instant between its call and its return, no two operations the same instant, called its point of effect (the field's word is linearization point). Second, the operations, taken in the order of these instants, form a sequential run of the specification in which each operation returns the value it returned in the history. The history then counts as explained by the sequential specification, for the stack by the sequential stack. An object is linearizable when every history it can produce is linearizable. Informally: each operation appears to the other threads to take effect at one instant between its call and its return. The points of effect are the prover's choice; the history, with its calls, returns and values, is what the run gave. A history may end with an operation that was called and has not returned, a push by a thread that the scheduler stopped in the middle of it; such an operation is either given a return value and a point of effect, or left out of the history, whichever makes the history linearizable.

The history of the figure, with the two pops returning the other way round: thread A's pop returns 1 and thread B's returns 2. Can this history be explained by a stack?

  1. No: thread A's push was called first, so 1 is below 2 and the first pop must return 2.
  2. Yes: the two pushes overlap, so their points of effect may be placed in either order, and with push(2) before push(1) the pops return 1 then 2.
  3. No: a history with overlapping operations is never explained by a sequential specification.
The answer

The second answer. The call to push(1) comes first, but push(1) has not returned when push(2) is called, so nothing a client can observe says which took effect first. Place push(2)'s dot before push(1)'s, both inside their bars: the sequential stack then holds 2 below 1, the pop that comes first returns 1, the other returns 2. The locked stack itself can produce this history: thread B may take the lock before thread A although A called first. A history that cannot be explained is one where both pops return 2, or where a pop returns a value never pushed: no placement of the dots makes a sequential stack do that. Two operations that do not overlap keep their order: the one that returned before the other was called has the earlier point of effect.

The locked stack is linearizable by construction. Under the lock the operations happen one after another; each holds the lock for its whole body, and so any instant inside its critical section serves as its point of effect. This holds provided block 1's obligation is met: every access to the stack's state is under the lock. A structure with one lock for the whole of it is called coarse-grained; the locked stack is the coarse-grained stack. Every observation that a client makes of the values returned by a linearizable stack, calling push and pop, is one that the coarse-grained stack could also give: each history of the linearizable stack is explained by a run of the sequential stack, and the coarse-grained stack produces that same history when each operation holds the lock at its point of effect. In that sense the coarse-grained version is the interface: what a client can observe of the values is all there. A client can still tell the coarse-grained stack from another by progress, which the progress conditions below make precise. The locked stack is the reference: a stack built without a lock meets the same standard for its values exactly when every history it can produce is explained by the sequential stack, as every history of the locked stack is. Whether its operations return is the separate standard of progress, next.

Progress conditions

Linearizability says what the values are. It says nothing about whether an operation ever returns. Block 1 defined safety and liveness: a safety property says that something bad never happens, and every run that violates it has a finite beginning in which the violation has already happened; a liveness property says that something good eventually happens, and no finite beginning of a run can show its violation. Linearizability is a safety property: a history that cannot be explained shows it in finitely many operations. The conditions on progress are liveness properties, and they are stated with a clause, "whichever threads are stopped", without which they would not be about progress at all.

A step is one instruction of a thread. In a run, some threads may be stopped at some point and never run again, by the scheduler or for any other reason; the others keep taking steps. A structure is blocking when a thread's progress in an operation can depend on another thread's being scheduled: a lock is blocking, since a thread that holds the lock and is stopped stops every thread that waits for that lock. A structure is non-blocking when no thread's progress depends on another thread's being scheduled.

Lock-free: in every run, from any point on, as long as at least one thread keeps taking steps inside an operation on the structure, some operation completes within finitely many further steps, whichever threads are stopped and whenever. Every lock-free structure is non-blocking. The slide draws blocking and lock-free on three threads, A stopped for good at a cross: under a lock, B and C wait for A's lock for ever; lock-free, B keeps completing while each of B's successes fails C's attempt, and C starves. The definitions are Herlihy's; the clause on stopped threads is the form Herlihy and Shavit gave them.2,3,25

The appendix sets out wait-freedom, the clause on stopped threads, and how the way a structure is built differs from the progress it guarantees.

Where block 1's way stands against these standards: a lock-based operation is linearizable by construction, and its progress is blocking. What this section leaves open is block 1's closing question, now sharpened: can an operation be linearizable and non-blocking? The next section gives one, on the counter.

2. Compare-and-set

Block 1 built a lock from one instruction, test-and-set, and put the counter's three steps, read, add, write, inside it. The second way removes the lock. In its place it uses one instruction of the same kind as test-and-set but stronger, compare-and-set, and lets the three steps run with no protection but a check at the end.

Compare-and-set (CAS in the figures) is an instruction on one memory location, a read-modify-write, that takes two values, the expected value and the new value. In one indivisible step it reads the location and, if the value read is the expected value, writes the new value; it reports whether it wrote. No thread sees between its read and its write. Like test-and-set, it also synchronizes: what the thread did before a compare-and-set that succeeded is ordered before what another thread does after reading the value that the compare-and-set wrote. Block 1's definition of a data race is now stated with the clause it needs: a data race is two accesses to one location from two threads, at least one a write and at least one of them a plain access, that is, not atomic, with no synchronization between them. Two accesses that are both atomic are therefore never a data race. That is the wording of OCaml's definition and of C++'s; Java reaches the same result because accesses to volatile fields and through the atomic classes used here are synchronization actions, all in one order.15,19 In OCaml the comparison is physical, the test ==: a value held in the word itself, an int or a constant such as [] or None, is compared by its value, and a value allocated in memory, a list cell for instance, by its address, so the location must hold the very same cell, not merely an equal one. In Java, compareAndSet on an AtomicReference compares references by identity, ==, never by equals. Fetch-and-add adds a number to the location and returns the old value, in one indivisible step, with the same synchronization. In Java these are compareAndSet and getAndAdd on an AtomicInteger, with getAndIncrement for adding one; in OCaml 5, Atomic.compare_and_set and Atomic.fetch_and_add, with Atomic.incr for adding one.

The counter on compare-and-set, and on fetch-and-add

Example 6, Java: CounterCas.java

static final AtomicInteger n = new AtomicInteger(0);   // the counter, one word
final int N = 1_000_000;                               // increments per thread

// returns how many attempts failed before the one that succeeded
static int increment() {
  int failed = 0;
  while (true) {
    int v = n.get();                              // read
    if (n.compareAndSet(v, v + 1)) return failed; // still v? then v + 1, in one step
    failed++;                                     // another thread wrote first: retry
  }
}

n.set(0);                                                 // the counter back to 0
Runnable work = () -> { for (int i = 0; i < N; i++) n.getAndIncrement(); };  // fetch-and-add
$ java CounterCas

The loop is the second way's whole mechanism. The thread reads the current value; it computes the new one, outside any protection; it asks the instruction to write it provided the location still holds what it read. If another thread wrote in between, the instruction fails, which detects the interleaving by what it changed; the thread retries from a fresh read. An attempt fails only when another thread's compare-and-set on the counter succeeded between this thread's read and its attempt; nothing else changes the counter. With two threads, each success of one thread makes at most one attempt of the other fail, since the other re-reads after it; so in this program at most two million attempts fail, and the sample's 653,147 is within that bound.

Two threads each call increment one million times. Can the total be wrong, and can an attempt fail?

  1. The total is exact, and no attempt ever fails.
  2. The total is exact; an attempt fails when another thread wrote the counter between this thread's read and its attempt.
  3. The total is wrong whenever an attempt fails.
The answer

The second answer. The run above is one sample: the total was exact and 653,147 attempts failed, each one an increment that read a value, found the counter changed, and read again. A failed attempt loses nothing, because the loop re-reads before it tries again, and the compare-and-set writes only when the counter still holds what was read. Whether the loop can spin for ever, so that the program never ends, is a further question, and in this program it cannot happen: a failure needs another thread's success, and the other thread succeeds at most a million times, so every loop ends. Whether it could happen in general is the question of progress, below.

The contract, the obligation, the progress, who checks

Block 1's way forbade the interleaving; this one accepts it, detects it and retries. Each way is stated in the four terms of the session's frame: the contract, what the way guarantees; the obligation, what the programmer must establish; the progress risk; and who checks the obligation.

The contract. The operation is atomic without exclusion, and linearizable: its point of effect is the compare-and-set that succeeds, the one indivisible step at which the counter changes. Every other step of the loop, the reads and the failed attempts, changes nothing that another thread can see.

The obligation. The loop re-reads: every attempt starts from a fresh read, never from a value kept from an earlier one. Every write keeps the invariant of the location; here the invariant is that every write replaces the current value v by v + 1, which the compare-and-set guarantees because it writes v + 1 only where the location still holds v. And the point of effect is named by the programmer, in a comment on the line and in the argument that the operation is linearizable, as section 3 makes for the stack.

The progress. A compare-and-set on the counter fails only because another thread's compare-and-set on the counter succeeded between this thread's read and its attempt. So every failed attempt is matched by an increment that took effect. Suppose some thread keeps taking steps in an increment that never completes: its attempts keep failing, and each failure needs a success by another thread since its read; a success ends that thread's increment, and that thread can succeed again only in a new increment, after returning from the old one; so increments keep completing. The loop is lock-free. It is not wait-free, which would require every thread to complete each of its operations within finitely many of its own steps: nothing stops one thread from failing at every attempt, another thread having written first each time; in principle that thread retries for ever while the others keep completing operations. The one-instruction version, fetch-and-add, is wait-free in the model of block 1, where one atomic instruction is one step: it takes no expected value and never retries, so it cannot fail, and each call is one step of its thread. Calls on one word from several threads do compete for the word, and the hardware orders them, but none is turned away. The model's step is one instruction of the machine where the processor has the instruction; where it has not, the library builds fetch-and-add as a loop of the same kind as the one above, which is lock-free.

Who checks. Nobody but the programmer, by proof. Java and OCaml accept a loop that keeps a value from an earlier read, a write that breaks the invariant, or a sequence of two atomic steps that was meant to be one. Section 3 shows that last mistake. Tools exist that check histories after the fact, and section 3 names them. Java's library offers the loop ready-made, updateAndGet with a function, and its documentation warns, as Clojure's documentation of swap! does in section 3, that the function may be run several times.

What this section leaves open: a counter is one word, and the whole state fits in the location the instruction covers. A stack is a structure of many nodes. The next section shows that the same loop serves, provided the structure is arranged so that one word is enough.

3. Treiber's stack

The method that makes the loop apply to a stack is to make one reference stand for the whole structure. A stack is a chain of nodes; if each node, once built, never changes, then the reference to the top node determines the whole stack, and changing the stack is changing that one reference. Treiber published the algorithm in 1986.4

An immutable node is a node whose fields are never changed after it is built; in Java, a record, whose fields are final. An atomic reference is a location holding a reference, read and written only by atomic instructions, compare-and-set among them; in Java an AtomicReference, in OCaml 5 an Atomic.t.

Example 7b, Java: Treiber.java

record Node(int value, Node next) { }             // immutable: final fields, never changed

// invariant: top points to a well-formed stack, a chain of nodes ending in null
static final AtomicReference<Node> top = new AtomicReference<>(null);

static void push(int x) {
  while (true) {
    Node old = top.get();
    Node fresh = new Node(x, old);                // built beside the stack
    if (top.compareAndSet(old, fresh)) return;    // point of effect: this compare-and-set
  }
}
static Integer pop() {                            // null when the stack is empty
  while (true) {
    Node old = top.get();                         // empty: point of effect is this read
    if (old == null) return null;
    if (top.compareAndSet(old, old.next())) return old.value(); // point of effect
  }
}

static void pushBroken(int x) {                   // broken on purpose
  Node old = top.get();                           // read
  top.set(new Node(x, old));                      // write: another push may have come between
}

Example 7b, OCaml 5: treiber.ml

(* Invariant: the atomic holds a well-formed stack, an OCaml list.
   The list is never changed, only replaced by another one. *)
type 'a stack = 'a list Atomic.t

let rec push (s : 'a stack) x =
  let l = Atomic.get s in
  (* Point of effect: the compare-and-set that succeeds. *)
  if not (Atomic.compare_and_set s l (x :: l)) then push s x
let rec pop (s : 'a stack) =
  match Atomic.get s with
  | [] -> None   (* Point of effect: the read that saw the stack empty. *)
  | x :: rest as l ->
      (* Point of effect: the compare-and-set that succeeds. *)
      if Atomic.compare_and_set s l rest then Some x else pop s
(* Broken on purpose: read the top, then write it, with no compare-and-set.
   A push by another domain between the get and the set is lost. *)
let push_broken (s : 'a stack) x =
  let l = Atomic.get s in
  Atomic.set s (x :: l)

How push and pop work

A push reads the current top, builds its new node, not yet reachable from the stack, with its next pointing at the top it read, and asks the compare-and-set to replace the top reference by the new node provided the top is still the one it read. If the top is no longer the node it read, because other threads pushed or popped in between, the attempt fails, and the push reads again and builds a new node. If other threads moved the top and moved it back to the very same node, the attempt succeeds, and rightly, since that node, never changed, still heads the same chain. A pop reads the top; if it is null, the stack was empty at that read and the pop returns null; otherwise it asks the compare-and-set to replace the top by the node below, provided the top is still the node it read, and returns that node's value. In both languages a read of the top is a snapshot of the whole stack, a complete stack as it was at the instant of the read, since the chain the top reaches never changes; the stack itself may move on after the read. In OCaml the snapshot is literally a value of the language, an immutable list, and the "node" of the figure below is one cell of the list.

The broken push

The broken push reads the top, then writes a new node above it with an atomic write alone, top.set in Java and Atomic.set in OCaml, no compare-and-set. Four threads push only, a million pushes in all, and the stack ends with 307,454 items. Where does it go wrong, and is it a data race?

  1. Between its read and its write another thread's push took effect; the write then installs a node pointing at the old top, and the other push is lost. Both accesses are atomic, so it is not a data race: it is an atomicity violation.
  2. The read and the write of the broken push are a data race, since nothing orders them against the other threads' writes.
  3. The immutable nodes are the problem: a node built before the top moved cannot be re-pointed, so its push is lost.
The answer

The first answer. Recall block 1's two words, with section 2's clause. A data race is two accesses to one location from two threads, at least one a write and at least one plain, with no synchronization between them; two atomic accesses to one location are never a data race. An atomicity violation is a multi-step operation not protected as a unit. The broken push is the counter's bug again, on a reference: a read and a write with a step of another thread between. It is the best example this session has of the two words told apart: no data race here, both accesses are atomic, and the bug is an atomicity violation without a data race. No run can settle the second half of the question; the definition does. The third answer is wrong: the lost pushes come from the write that is not a compare-and-set, not from the nodes. A node whose compare-and-set failed was never installed, so no other thread can reach it, and re-pointing it before the next attempt would be just as correct as building a new one. What matters is that a node never changes once another thread can reach it: then the chain below a node that a thread has read is fixed, which the proof sketch uses.

The proof sketch

The standard of section 1 is that every history be explained by the sequential stack, and that progress be guaranteed. The argument has four parts, the invariant, the points of effect, safety and liveness, and each names something in the code; a remark on who checks follows it.

The invariant. The top reference points to a well-formed stack: a chain of nodes ending in null, each node immutable once another thread can reach it. The stack that the top stands for is the list of the values read from the top node down to null; the invariant makes this list well defined. The invariant holds at the start, when the top is null. Every write to the top is a compare-and-set, and each one keeps it: a push installs a node whose next is the top it read, which was well-formed, and the node never changes; a pop installs the next of the top it read, which is the rest of a well-formed chain. A failed attempt writes nothing.

The points of effect. A push takes effect at its compare-and-set that succeeds. A pop on a non-empty stack takes effect at its compare-and-set that succeeds. A pop on an empty stack takes effect at the read that saw the top null: at that instant the stack was empty, and the sequential pop of an empty stack returns null. Each of these is one indivisible step inside the operation's call and return.

Safety, which is linearizability. Order the operations of a history by their points of effect. Between two consecutive points of effect the top does not change, since failed attempts and reads write nothing. Each point of effect does to the stack that the top stands for exactly what one sequential push or pop does. A successful push's compare-and-set replaces the top by a node whose next is the top that was there, which adds one value on top, as the sequential push does. A successful pop's compare-and-set replaces the top by the node below it, which removes the value on top, as the sequential pop does. An empty pop's read changes nothing, as the sequential pop of an empty stack changes nothing. So the sequence of stacks the top stands for is exactly the sequence of states a sequential stack passes through when the operations are applied in the order of the points of effect. And each operation returns what the sequential stack returns at that point: a pop returns the value of the node that was the top at its point of effect, which is the value the sequential pop removes; an empty pop returns null when the sequential stack is empty. An operation stopped after its successful compare-and-set has taken effect, and is given the return value the sequential stack gives at that point; one stopped before has written nothing and is left out. The history is explained by the sequential stack.

Liveness. As for the counter. A compare-and-set on the top fails only because another compare-and-set on the top succeeded between this thread's read and its attempt, and that success is the point of effect of a push or a pop. Suppose some thread keeps taking steps in an operation that never completes: its attempts keep failing, each failure needs a success by another thread since its read, a success ends that thread's operation, and that thread can succeed again only in a new operation after returning from the old one; so the successes go on, and as there are finitely many threads, some thread completes operations again and again. The stack is lock-free. It is not wait-free: every attempt of one thread may fail.

A top that changes and comes back between a thread's read and its compare-and-set is the ABA problem; the appendix treats it, with a garbage collector and without one.

Who checks. The programmer, by this proof. The types check part of the invariant: in OCaml the type 'a list Atomic.t guarantees a well-formed chain of immutable cells outright, and in Java the record's final fields guarantee that a node never changes. Nothing in either language checks that every write to the top is a compare-and-set from a fresh read, or where the points of effect are; the broken push compiles and runs. At test time there are checkers that take a recorded history and search for a placement of the points of effect that the sequential specification accepts: Lincheck for Java and Kotlin, which generates the concurrent runs as well; Knossos and Porcupine, which take histories. They do not replace the proof; they are what practice uses, and the mini-project's checker is one of this kind.

The bridge to Part 1

A data structure is persistent when an update leaves the old version usable and gives a new one; the usual way, Part 1's, is for the new version to share the unchanged part of the old, and Part 1's lists and ropes were persistent. What made the stack fit in one word is a persistent value: the chain of immutable nodes. Treiber's stack is a persistent value behind one atomic reference, and an operation is one compare-and-set on that reference. Herlihy made this general in 1993.3 For an object small enough to copy, an operation reads the reference to the object, copies the object, applies the sequential operation to the copy, and then replaces the reference by one to the copy, retrying when the replacement fails. The replacement in Herlihy's protocol is a store-conditional, the write half of a pair of instructions, load-linked and store-conditional, where the store succeeds only if nothing has written the location since the load; on compare-and-set the same protocol needs the collector against ABA, as Treiber's stack does. For an object too large to copy, the operation builds a new version that shares what it does not change, which is exactly a persistent update, and replaces the reference to the root by one to the new version. Clojure's atom is one atomic reference holding an immutable value, and swap! is Herlihy's protocol as a library call on compare-and-set: it reads the atom's value, applies the given function, and attempts a compare-and-set, retrying in a loop. It may run the function several times, so the function must have no effects; nothing checks it. In the course's three runs, eight threads doing 800,000 swaps in all each run had the function called between 4.2 and 4.6 million times, each call beyond one per swap a retry. Java's updateAndGet on an atomic reference is the same loop, with the same warning in its documentation.13

What this section leaves open: whether a structure without a lock is always the better choice, and whether every structure has such a version.

4. Contention

Section 3 answered block 1's question: an operation can be atomic without a lock around it, and a proof sketch establishes it. Two further questions follow at once, whether lock-free is always best and whether every structure has a lock-free version; this section answers the first.

Whether lock-free is always best

Not always, for two reasons: contention, and an uncontended lock, which costs no more than one attempt of the loop.

Contention. Contention is several threads wanting the same word at the same time. Every failed compare-and-set is wasted work, and when many threads retry on one word, the top of the stack for instance, most attempts fail: every operation on the stack passes through the top, which Hendler, Shavit and Yerushalmi, who built a faster stack on Treiber's, call a sequential bottleneck.11 The clearest measurement is flat combining, by Hendler, Incze, Shavit and Tzafrir. Each thread writes the operation it wants into a shared list of requests; one thread takes a coarse lock and performs all the requests it finds there, one after another, while the others wait for their results. On a Sun SPARC T2 machine, measured from 1 to 64 threads, their flat-combining queue overtakes Michael and Scott's lock-free queue from about four threads on and is four to seven times faster at the higher thread counts; their flat-combining stack is up to nine times faster than Treiber's stack, whose top is the bottleneck.10 Flat combining is lock-based and blocking. So a structure with a lock can be faster than a structure without one.

The uncontended lock. Taking a lock that no thread holds is itself one atomic instruction, the test-and-set of block 1's spin lock, the same kind of step as one compare-and-set attempt. Each is costly when several threads want the word, and neither is costly when no other thread does.

The appendix sets out operations on the whole structure, the case where only a non-blocking structure will do, and the universality of compare-and-set, which answers the second question.

What this section leaves open: the second way keeps the sharing and pays for it in retries. The third removes the sharing itself.

5. Deterministic parallelism

The first two ways accept that the threads share state and make its operations atomic, by exclusion or by one instruction. The third way arranges the work so that the order in which the threads run cannot change the result. Then no interleaving is harmful, and nothing has to be forbidden or redone.

A count per thread, then the sum

Example 8 (a), Java: PerThread.java

final int N = 1_000_000;
long[] counts = new long[2];                    // slot t written by thread t, read after join
Thread[] ts = new Thread[2];
for (int t = 0; t < 2; t++) {
  final int id = t;
  ts[t] = new Thread(() -> {
    long mine = 0;                              // local: no other thread sees it
    for (int i = 0; i < N; i++) mine++;
    counts[id] = mine;
  });
}
for (Thread t : ts) t.start();
for (Thread t : ts) t.join();
System.out.println("expected " + 2 * N + ", got " + (counts[0] + counts[1]));

This is the counter's third version in this session, after the lock of block 1 and the compare-and-set of section 2: exact, with no lock and no atomic instruction. Each thread counts in a variable of its own, which no other thread can reach; the order in which the threads run cannot matter, because nothing is shared while they run. Nothing shared while the threads run means, precisely, that no location written by one thread is read or written by another thread while they run. At the end the counts are added by one thread, after the others have ended. One sample; ten more runs printed the same.

One line carries the whole argument, and it is the join. In the Java program the array counts is shared, but each slot of it is written by one thread only, and the main thread reads the slots after join, which orders each thread's last step, its write of its slot, before the main thread's read. The join is what makes each count visible to the thread that sums. Without the join the same program has a data race by block 1's definition: two accesses to one location from two threads, one a write, with nothing of the program ordering them. The main thread may then read a slot before or after its one write, and the program may print 0, one million or two million; a slot is a long, so Java would also allow a value made of half of each write, which here gives nothing new, since both values, 0 and one million, have zero in their high 32 bits. In the OCaml program the count comes back as the value Domain.join returns, with no shared variable in the program; the join still carries the argument, since everything the domain did is ordered before the join returns. The first of the lab's questions on paper asks the same of a worker that writes its result into counts[id]: what the main thread may read there before the join, after the join, and after joining only the other workers.

A pure function is one whose result depends on its arguments only and that changes nothing outside itself; a map over a sequence applies a function to each element and collects the results, a word the course uses in this sense only, never for a dictionary. A parallel map is the same arrangement as the count per thread, over a sequence. With a pure function the elements' results are independent, so any thread may compute any of them in any order, and the only shared step is putting each result in its own slot. No program for it here; in Java the library's parallel streams, which run a map or a fold over a collection on several threads, do it.

The parallel fold

A fold combines the elements of a sequence with a binary operation, starting from a seed, from left to right: the fold of 1, 2, 3 with subtraction from 0 is ((0 − 1) − 2) − 3. A parallel fold splits the sequence into parts, folds each part on a thread of its own from the seed, and combines the parts' results in their order, as a tree: with the parts' results p0, p1, p2, p3, two halves give p0 op p1, four quarters give (p0 op p1) op (p2 op p3). A split is one way of cutting the sequence into parts. An operation is associative when (x op y) op z = x op (y op z) for all x, y, z; it has an identity e when e op x = x = x op e for all x; it is commutative when x op y = y op x for all x, y.

Example 8 (b) and (c), Java: PerThread.java, the fold

// one thread per part folds its part from e, from left to right;
// then the main thread combines the parts' results as a tree:
// two parts p0 op p1, four parts (p0 op p1) op (p2 op p3)
static long fold(long[] a, int parts, long e, LongBinaryOperator op)
    throws InterruptedException {
  long[] partial = new long[parts];
  Thread[] ts = new Thread[parts];
  int size = a.length / parts;
  for (int p = 0; p < parts; p++) {
    final int lo = p * size, id = p;
    ts[p] = new Thread(() -> {
      long acc = e;
      for (int i = lo; i < lo + size; i++)
        acc = op.applyAsLong(acc, a[i]);
      partial[id] = acc;
    });
  }
  for (Thread t : ts) t.start();
  for (Thread t : ts) t.join();
  for (int n = parts; n > 1; n /= 2)    // one level of the tree
    for (int p = 0; p < n / 2; p++)
      partial[p] = op.applyAsLong(partial[2 * p],
                                  partial[2 * p + 1]);
  return partial[0];
}

In the Java fold, LongBinaryOperator is the library's type for a function of two long arguments, applied with applyAsLong; the last loop combines the parts' results level by level, two parts at a time, which for four parts is (p0 op p1) op (p2 op p3). The parts are combined in their order, after every thread has been joined, never in the order the threads finish. As written, the Java fold assumes that the number of parts is a power of two and divides the length of the array; with three parts it would drop the third part's result, and the test's fold of question 11, with its three pairs, is a different program.

The array is 1 to 8 and the seed is 0. The sequential fold with subtraction, one thread from left to right, gives −36. Does the parallel fold with subtraction agree with it in two halves? In four quarters? Does its answer change from run to run?

  1. Yes, yes, no: a fold is a fold, and the threads only share the work.
  2. No, no, no: the two halves give 16 and the four quarters give 0, and each grouping prints the same number on every run.
  3. No, no, yes: the result depends on which thread finishes first.
The answer

The second answer. Two halves: (0 − 1 − 2 − 3 − 4) − (0 − 5 − 6 − 7 − 8) = −10 − (−26) = 16. Four quarters: ((0 − 1 − 2) − (0 − 3 − 4)) − ((0 − 5 − 6) − (0 − 7 − 8)) = (−3 + 7) − (−11 + 15) = 4 − 4 = 0. The parts are always combined in their order, after every thread has been joined, so the interleaving plays no part and each grouping is deterministic: ten more runs printed the same. What fails is agreement across splits, not across runs. The intended specification is "the same answer as the sequential fold, for any number of threads", and subtraction breaks it because it is not associative. Question 11 of the session's test-yourself page asks the same of a fold of 1 to 6 whose parts start from their first element instead of a seed; it gives 3 in two halves and 1 in three pairs by the same arithmetic.

Associativity is what guarantees the specification, the same answer as the sequential fold for every split, provided that op is a function without side effects: it changes no state, and its result depends only on its arguments. An op that also wrote to a shared variable, or read a clock, could give a different answer from run to run, whatever its associativity. For an associative operation, every bracketing of x1 op x2 op … op xn gives the same value; so, when every part is folded from the identity, every split of the sequence agrees with the sequential fold, whatever the number of threads. Every part needs the identity, not only a part with no elements: each part is folded from the seed, so the seed must be a value that changes nothing when combined, or it is counted once per part; with seed 5 and addition, two halves give 46 against the sequential 41. A part with no elements must fold to that value. Zero is not an identity of subtraction, since x − 0 = x but 0 − x ≠ x. In two halves, the first part starts from 0, as the sequential fold does, and gives −10, the value the sequential fold reaches after 1 to 4; the error enters with the second part, which starts from 0 instead of continuing from −10, and the combine −10 − (−26) gives 16 where the sequential fold gives −36. Combining the parts in their order is what makes associativity enough: the program joins every thread and then combines p0 with p1, then with p2 and p3, in the order of the sequence. A program that combined the parts in the order the threads finish would need the operation to be commutative as well. Addition of integers is both, even when it overflows, since Java's long and OCaml's int wrap around; addition of floating-point numbers is commutative and not associative, so a parallel sum of doubles may differ from the sequential sum in its last digits, and differ again with another number of parts. Concatenation of strings is associative and not commutative, and a parallel fold with it is right exactly because the parts keep their order; maximum is both, with the smallest number the type can represent as its identity. Java's library states the same condition in its own words: Stream.reduce requires an identity and an operation that is associative and, in the library's words, non-interfering and stateless.13

The three forms of the third way

The independence of the order comes in three forms.

First form: no shared mutable state during the run, and a combine step
The count per thread, the parallel map, the parallel fold. The threads share nothing that any of them writes while they run; a combine step after the join puts the results together. The obligation is that the combine is a function without side effects, associative with an identity, and that the parts are combined in their order, or, if they are combined in the order the threads finish, that the combine is commutative as well.
Second form: updates that commute, each applied as one step, or to a replica of its own that is merged at the end
Two updates commute when applying them in either order gives the same state. Increments commute; so do insertions into a set. Applied as one step, fetch-and-add on one word: the interleaving still orders the steps, and commutativity makes the final state the same for every order; the step itself is made atomic by the first way or the second, and what commutativity adds is that the final state does not depend on the order the steps took. The Java library's LongAdder is this case made faster: under contention it spreads the updates over several cells, each updated by compare-and-set, so that fewer threads compete for any one word; sum adds the cells, and is not an atomic snapshot of them.13 Applied to a replica, a copy of the state that one thread alone updates and that is merged with the others at the end: a set per thread, merged by union; the structures session 9 calls CRDTs, conflict-free replicated data types, replicas merged by an operation that is commutative, associative and idempotent, so that merging in any order and any number of times gives one state. The condition is the atomic step or the private replica. Commuting updates that are not atomic are the racy counter of block 1: its increments commute, and it loses updates, because the read, add and write of one increment interleave with another's. Commutativity of the updates does not make the counter correct unless each update is atomic.
Third form: determinism by construction
Languages in which every interleaving gives the same result, by the rules of the language. Dataflow: a program is a network of sequential programs, each with memory of its own, connected by unbounded queues, each queue written by one program and read by one. Kahn showed in 1974 that such a network computes the same function whatever the schedule, provided that each program is deterministic, reads each of its input queues in order, waits when a queue is empty, and never tests whether a queue is empty.9 Single-assignment variables: a variable written once, a second write being an error, and a read that waits until the write has happened, so that no read can see a value that a different order would have changed.

Immutability is not a fourth way. It is a technique that serves the second way, Treiber's immutable nodes and Herlihy's copy-and-swap, and the third, where nothing is shared because nothing is mutable.

The counter against the stack

For the counter every way gives the same final value, because increments commute: once each increment is atomic, under a lock or by one instruction, or is made in a slot of its own, the order of the steps does not show in the result. For a stack shared while the threads run, two pushes do not commute, and the pops show which came first; so the stack's result depends on the interleaving under every way, and the only demand on it is that each run be explained by some order, which is linearizability. The third way is for work whose intended result is one value, the same for every order: a count, a sum, a fold. Its second form needs updates that commute; its first needs only a combine that is associative and is taken in the order of the parts, which is why concatenation, and a stack that each thread builds for itself and that the parts concatenate in order after the joins, are third-way work; its third form needs neither. Threads that push and pop on one shared stack, each using what its pops return while the threads run, have no such result: which pop returns which value depends on the order, and the specification of the stack allows every order. That is why the third way applies to the counter and not to a shared stack, and why linearizability is the whole demand on the stack.

The contract, the obligation, the progress, who checks

The contract: a deterministic final result, the same in every interleaving; the values an atomic step returns on the way, the old value of a fetch-and-add for instance, still depend on the order. The obligation: one of the three forms, in full: nothing shared while the threads run and a combine without side effects that is associative with an identity, the parts combined in their order; or updates that commute, each applied as one step or to a replica of its own merged at the end; or determinism by construction. The progress risk: none from the interleaving; but the join is blocking in the sense of section 1, since the thread that combines waits for every worker, and a worker that is stopped stops the result. What the way costs besides is the combine step, which runs after the threads it waits for. Who checks: that nothing is shared while the threads run, the type system can check. In Haskell a pure function cannot touch mutable state: a mutable variable is a cell that only code whose type shows it may write, IO for an IORef, and the compiler rejects a function of type Int -> Int that tries to write one, with the error "Couldn't match expected type ‘Int’ with actual type ‘IO Int’".23 In Rust the compiler checks that each thread owns its slot: the right to change a value, a mutable borrow, is given to one holder at a time, and the right to read it, a shared borrow, to any number; in the per-thread count under thread::scope each thread holds the mutable borrow of a different slot and a shared borrow of its own part of the data, with no lock and no atomic, and the scope ends before the slots are read.18 That the combine is associative, or that the updates commute, nobody but the programmer checks: the fold with subtraction type-checks in Haskell and in Rust as it does in Java.

What this section leaves open: all three ways make one operation atomic, or make one result order-independent. The transfer of block 1 needs two operations to be one. Two atomic operations compose when the operation that performs the one and then the other is itself atomic, so that no other thread can observe the state between them; the next section shows whether atomic operations compose.

6. Composition

Block 1 showed the transfer: a withdrawal under the source's lock, then a deposit under the destination's lock, each atomic, and a third thread reading both balances under both locks saw 199 where the sum should be 200. Two atomic steps are not one atomic step. The same holds for the second way: a compare-and-set on the source and a compare-and-set on the destination are two points of effect, and a reader may fall between them. Neither locked nor compare-and-set operations compose by themselves into one atomic operation.

Two senses of "compose"

Herlihy and Wing proved that linearizability is local: a history over several objects is linearizable if and only if each object's own part of it is.1 So two linearizable objects used together are still a linearizable system, each operation at its own instant; in that sense linearizability composes across objects, a sense different from two operations composing into one. Locality is what tells linearizability apart from sequential consistency applied to objects, which keeps each thread's order but not the real-time order between threads and does not compose across objects. What is not given is one instant for two operations: the withdrawal and the deposit each have their own point of effect, and nothing makes them one. The system of two accounts is linearizable; there is no operation on both accounts that takes effect at one instant, which is what a transfer would be.

Three ways give two operations one instant: both locks held around both steps, both accounts behind one reference, or a transaction; the appendix sets out each, with its price.

What this section leaves open: every argument of this session has rested on the assumption that a run is an interleaving. Section 7 says who guarantees that.

7. Memory models

Block 1 began with four assumptions about the machine. The fourth was said once and not explained: there is one memory, and every read returns the value of the latest write before it in the interleaving, which Lamport in 1979 called sequential consistency;5 and the language guarantees it for every program none of whose interleavings has a data race. Every argument since has used it: the exactness of the counter under the spin lock, the points of effect of this block. Even the lost update of the racy counter was explained by an interleaving, although that program is outside the guarantee, as this section's question shows. This section says what the assumption was.

The memory model's guarantee

It is a guarantee, and the one that gives it is the language's memory model: the part of a language's definition that says which values a read may return in a multi-threaded program. A processor and a compiler reorder a thread's reads and writes for speed, so that another thread may see them in an order other than the program's. The slide's example: thread 1 writes x = 1 and then y = 1; with the two writes swapped by the processor, thread 2 may read y as 1 and then x as 0, which no interleaving of the two threads' steps gives. Adve and Hill proposed the guarantee in 1990 as a contract between programs and hardware: a program that is free of data races may be run by a machine that reorders memory operations, and will still behave as if the memory were one sequence of operations.6 The literature calls this guarantee DRF-SC, sequential consistency for data-race-free programs. The languages took it over as a contract between programs and the language. Java guarantees it for correctly synchronized programs, those none of whose interleavings has a data race, in chapter 17 of its specification.15 C and C++ guarantee it for programs that synchronize with mutexes and with default atomics only, atomic accesses that ask for the strongest ordering, under which all atomic accesses fall in one order that every thread sees the same.16 Rust's memory model is C++'s, with the same condition on its atomics.18 Go guarantees it in its memory model of 2022.17 OCaml 5 guarantees it on the model of Dolan, Sivaramakrishnan and Madhavapeddy.7,19

The condition is the one block 1 defined, with section 2's clause. A data race is two accesses to one location from two threads, at least one a write and at least one of them a plain access, with no synchronization between them; and synchronization is the order a lock's release gives before its acquire, a thread's start before its first step and its last step before the join that waits for it, an atomic or volatile write before the read that sees it; and in each case the order carries everything the first thread wrote before its release, its last step or its write. Program by program, this is what made the guarantee apply. The spin lock's program was race-free because test-and-set synchronizes, block 1's second guarantee of the instruction: what one thread did before releasing the flag is ordered before what the next thread does after acquiring it, provided the flag is released by an atomic write, as block 1's spin lock does; so the plain counter inside the lock is never accessed by two threads without that order. The count per thread was race-free because of the join. The compare-and-set loop and Treiber's stack were race-free because every access to the top is atomic, and a node's fields are written only before the node is published through the top and read only after it was read from the top, which the atomic orders. In each case the guarantee applied, every run behaved as some interleaving, and the reasoning by interleavings was sound.

What a racy program gets, language by language, from each language's own definition. A race is bounded in space when it affects no location but the one raced on, and bounded in time when it affects no access to that location before or after the racing ones.

  • C and C++: undefined behaviour, which means that the standard places no requirement on what the program does. The compiler may act on it: in the course's run a compiler at its usual optimization level removed a loop that waited on a plain flag, and the program read the data before the flag and printed the value from before the write.16
  • Java: the behaviour is defined, and bounded in space. A read returns a value that some thread wrote to that variable, never a value that no thread wrote, and the program's objects stay intact; but a race is not bounded in time, a race on one variable can affect later reads of it, and a long or double that is not volatile, a 64-bit value, may be read as one 32-bit half of one write and the other half of another, which the specification allows although most 64-bit machines do not do it.15,7
  • OCaml 5: the behaviour is defined, and bounded in space and in time. If no access to a location races during an interval of a run, meaning that every write to it by another thread is ordered before or after the interval by synchronization, then the accesses to it in that interval behave as in an interleaving, whatever races happen on other locations or at other times; this is the local data-race freedom of Dolan, Sivaramakrishnan and Madhavapeddy, and the manual's chapter lists the operations outside the guarantee.7,19
  • Go: like Java for one word, a read sees a preceding or concurrent write and nothing out of thin air; a race on a value of several words can corrupt memory arbitrarily; an implementation may also report the race and halt.17
  • Rust: no data race can be written in safe Rust. Ownership rejects a variable that two threads can reach while one changes it, unless a lock or an atomic stands between, and two marks on types, Send and Sync, say which values may be given to or shared with another thread; the guarantee assumes that the code marked unsafe underneath, where the check is off, keeps its guarantees. Deadlocks and race conditions remain: a race condition is a wrong result that depends on the order of events, with or without a data race, and the transfer in two halves is one.18

The reader's two reads are each a data race with the transfers' writes. The program compiles and runs with no warning, in Java and in OCaml. What does the language guarantee for this program?

  1. Nothing: a program with a data race has no defined meaning in any language.
  2. That every run is some interleaving of the threads' steps, since the transfers themselves are correctly locked.
  3. That the guarantee of an interleaving is off for this program; what is left depends on the language, and in Java and OCaml the damage is bounded.
The answer

The third answer. The guarantee holds for programs none of whose interleavings has a data race, and this one has; so nothing guarantees that a run is an interleaving. What is left is what each memory model says about a racy program, and that differs from language to language, as the list above says. The wrong sums inspected are of the kind an interleaving gives, the reader's two reads falling on either side of a transfer's two writes, so that the sum is off by one. Neither language guarantees even that: Java bounds a racy read only to some value once written to that variable, possibly an old one, and the two plain reads may be reordered; nothing worse showed in this run, on this machine, and the record does not say that every wrong sum was 199 or 201. No run can decide between the second and the third answer; the definition does. The first answer is true of C and C++ and false of Java, OCaml and Go. In OCaml the two reads of the tuple are evaluated in an order the language does not fix, which changes nothing here, since either order can fall around a transfer.

The languages also differ in how much control they give over the order of memory operations; an access mode is the strength of ordering that one read or write asks for. C++ and Rust let the programmer choose an access mode for each atomic access. Java offers four access modes, plain, opaque, release and acquire counted as one, and volatile, a series in which each mode gives every guarantee of the mode before it and more.20 OCaml offers two modes only: its plain fields, stronger than Java's plain mode since a race on them is bounded in time, and its atomics, which behave like Java's volatile.7 Go offers no choice: all its atomic operations have the strongest mode. These notes take the access modes no further.

This answers question 2 of the session's test-yourself page as well. Provided that every atomic access uses the strongest mode, the absence of data races guarantees that every run behaves as some interleaving of the threads' steps. In Java the strongest mode is that of volatile fields and of the ordinary methods of the atomic classes (get, set and compareAndSet among them, which have the semantics of volatile accesses); in OCaml every atomic has it; in C, C++ and Rust it is the sequentially consistent ordering. The absence of data races guarantees nothing more: which interleaving is not fixed, so runs differ; locks taken in a cycle still deadlock; and a counter with a lock around each of its three steps has no data race and still loses updates.

What this section leaves open: a type system that checks more than the absence of data races, session 12.

Wait-freedom and the clause on stopped threads

Wait-free: in every run, every thread that keeps taking steps inside an operation completes that operation within a finite number of its own steps, whichever other threads are stopped and whenever. Every wait-free structure is lock-free. On the slide's three threads, A stopped for good at a cross, B and C both complete.

The clause "whichever threads are stopped" is what makes these conditions about progress rather than about one particular run. Without it, a lock would count as lock-free: if the scheduler lets the thread that holds the lock run, that thread finishes its operation. With the clause, a lock is not lock-free: stop the holder, and no operation ever completes, however many steps the others take. "Finitely many" is a bound that exists, not a small one: the condition rules out waiting for ever, not waiting long. In older papers, among them Michael and Scott's, "non-blocking" is used for what this block calls lock-free.12

Construction and progress

Two pairs of words keep one meaning each throughout the session. Lock-based and without locks say how a structure is built. Lock-free and wait-free say what progress it guarantees, and nothing else. A structure built without locks is not thereby lock-free, and a lock-based structure is never lock-free, since stopping the holder stops every waiter. The Disruptor is a queue over a ring buffer, an array used in a circle, whose authors call it lock-free in the sense that its path has no lock; a thread that puts claims a slot and then publishes it, and a putter stopped between the two stops every thread that takes once it reaches that slot, which is blocking.21 Three more terms describe how a structure is built; they are defined here so that the reader meets them with a meaning, and the lecture does not use them. A fine-grained structure has a lock per part, a node of a list for instance, where the coarse-grained one has one lock for the whole. An optimistic operation reads without a lock and checks, before writing, that what it read still holds. A lazy removal first marks an element as removed and only later takes it out of the chain.

The ABA problem

The ABA problem, and why it does no harm here. The ABA problem is this hazard: a thread reads the value A from a location, meanwhile other threads change the location to B and back to A, and the thread's compare-and-set, expecting A, succeeds although the structure it reasoned about has changed. Values do return to the top of this stack. Between a thread's read and its compare-and-set, other threads may push a node and pop it again, and the top is once more the very node the thread read, or the empty stack, null or [], once more. That return is harmless: the very same node, never changed, heads the very same chain, so a compare-and-set that succeeds against it is right. The harmful case is a different node at the same address. In a language with a garbage collector, the part of the runtime that frees memory no thread can reach any more, Java and OCaml among them, that case cannot arise for this stack: a node that any thread still holds a reference to is never freed, so its address is never reused, and every push allocates a fresh node. A thread whose read is stale then finds a new node at the top, not the one it read: its compare-and-set fails and it reads again, which is what the slide shows with the node 9. The garbage collector removes ABA for a structure that allocates a fresh node for every push and compares references. A program that reuses its own nodes, from a pool of its own, or whose compare-and-set compares numbers that stand for a structure, an index into an array for instance, meets ABA again, collector or not; Java's AtomicStampedReference, a reference paired with a counter, is the library's answer for that case. Without a collector, in C or C++, a popped node may be freed and its memory reused for a new node at the same address, and a pop whose read is stale meets two hazards. If it reads the next of its node after that node was freed, it reads freed memory: a use after free. If it read next before the frees, as thread 1 does in the figure, its compare-and-set, expecting the old address, finds the new node at that address, succeeds, and installs as the top a node that was freed: the stack is corrupted. Two techniques exist for that case, hazard pointers and epochs, and both delay the freeing of a node until no thread can still hold it.

Operations on the whole structure, and the progress guarantee

The operations on the whole structure. A structure whose nodes change in place has no instant at which the whole of it is unchanged by the other threads. The Java library's ConcurrentLinkedQueue, built on Michael and Scott's lock-free queue, documents the consequence: its size needs a traversal of the whole queue and may report an inaccurate result if the queue is modified meanwhile, so it "is typically not very useful in concurrent applications"; a traversal of its elements is weakly consistent, which means that it shows no element twice and shows every element present from its start to its end, but may or may not show the elements added or removed meanwhile, so that what it shows need not be the content of the queue at any one instant; and an operation on many elements at once, adding a whole collection for instance, is not atomic.13 Under a lock, size and iteration are one critical section each. A persistent structure behind one reference, Treiber's stack among them, does have such an instant, the read of the reference, which is why its size and its traversal are linearizable at that read; the price is the one paid at the single reference.

Where it wins. The progress condition is the point, not speed. A thread that holds a lock and is stopped, by the scheduler, by the operating system while it brings in the memory the thread touched, or by waiting for a device inside its critical section, stops every thread that waits for the lock; block 1's Pathfinder, where a stopped holder held up a more urgent thread, is the case. A thread stopped in the middle of a push on Treiber's stack stops nobody: it holds nothing, and every other push and pop goes on. Where a stopped thread must not stop the others, only a non-blocking structure, lock-free or wait-free, will do. The guarantee is the algorithm's, in the model where allocating a node is one step; the runtime underneath can still stop every thread, as a garbage collection does.

Whether every structure has a lock-free version

Yes, by a general construction, and the construction is slow. Herlihy proved in 1991 that compare-and-set is universal: with compare-and-set and a fixed, known number of threads, any object with a sequential specification has a wait-free, linearizable implementation.2 Herlihy ranks the instructions by their consensus number, the number of threads for which the instruction lets every thread agree on one value, wait-free: reads and writes have number 1; test-and-set, fetch-and-add, and a stack or a queue shared by two threads, number 2; compare-and-set, and load-linked with store-conditional, every number, which is what makes them universal. He also proved that with reads and writes alone not even a queue that two threads may both take from can be built, wait-free, and the same holds for a stack; the lock-free case follows, since the proof lets each thread do one operation. The construction is a proof, not a program. Every operation is appended, one after another, to one shared list of all the operations ever requested, and every thread applies that list in the same order to a copy of its own; a thread that appends also appends the announced operation of a thread whose turn it is, which is what makes the construction wait-free rather than lock-free. So nothing runs in parallel, and the construction needs memory cubic in the number of threads and a number of steps per operation that grows as a higher power of it, by the paper's own count. Michael and Scott state the consequence: implementations from general methodologies are "generally inefficient compared to specialized algorithms".12 The efficient structures each exploit something the general method cannot see. A queue has two ends, and Michael and Scott's queue lets a put and a take proceed on each end at once. A stack has cancelling pairs: in the elimination stack of Hendler, Shavit and Yerushalmi, a push and a pop that meet in a side array exchange the value and both complete without touching the stack, which is where the stack's parallelism comes from.11 A counter's additions commute, and section 5 shows what the Java library makes of that. No method yet derives an efficient lock-free structure from a sequential specification alone, and each fast structure is a paper of its own.

What composes, and at what price

Locks compose by hand. One critical section around both steps, holding both locks, makes the transfer one operation; block 1 showed the cost, deadlock when two threads take the locks in opposite orders, and the repair, a global order of the locks. The obligation grows with every lock the operation touches.

One compare-and-set covers one reference. Treiber's stack showed that the reference may stand for a whole persistent structure. Put both accounts behind one reference to a persistent dictionary, from account names to balances, that is updated by building a new version, and the transfer is one swap: read the dictionary, build a new dictionary with both balances changed, compare-and-set the reference. It is correct and it composes with every other operation on the dictionary, at the cost that every update of the dictionary now competes for that one reference and retries against every other. That cost is the cost of Clojure's atom of section 3. Compare-and-set on several words at once exists as a technique, multi-word compare-and-set, and OCaml 5 has a library for it; the lecture does not use it.26 Clojure's refs, references that only a transaction may change, are the way to have several references and still compose.

A transaction is a block of reads and writes on several locations whose writes take effect together, at one instant, or not at all. The runtime, the part of the language's implementation that runs along with the program, detects a conflict with another transaction and then discards the transaction's writes and runs it again. Software transactional memory, STM, is a runtime that provides transactions on a program's memory. What counts as a conflict differs between systems, and the difference matters below. Harris, Marlow, Peyton Jones and Herlihy state the contrast in their own words: "lock-based programs do not compose: correct fragments may fail when combined", whereas "transactions are compositional: small transactions can be glued together to form larger transactions", in sequence and, in their system, as alternatives, the second transaction tried when the first cannot proceed.8

Two observations, both from the course's runs. In Haskell, the counter as a transaction, atomically $ modifyTVar' tv (+ 1) from two threads, which adds one to the transactional variable tv inside a transaction, was exact in ten runs of ten; that shows the step atomic, not yet composition. The compiler rejects a transaction that prints: "Couldn't match type ‘IO’ with ‘STM’", because a transaction may be run again and the type keeps irreversible actions out of it.23 Haskell's STM reruns a transaction when anything it read has changed, so every run is explained by running the transactions one at a time. In Clojure, the transfer is one transaction over two refs, (dosync (alter from - amount) (alter to + amount)), which subtracts from one ref and adds to the other inside one transaction. Eight threads made 800,000 transfers in both directions; the total was 2000 at the end; a reader that took both balances inside one dosync never saw a total other than 2000 in 4,352,597 reads, and a reader that took them outside any transaction saw a wrong total 5,345 times.14 That is composition: the two halves of the transfer appear to every reader inside a transaction as one step. The consistency belongs to the transaction, not to the refs. Clojure's transactions give snapshot isolation: every read in a transaction sees the state as it was when the transaction started, and a transaction is run again only when another has committed a write to a ref that it also writes, or to a ref that it has read with ensure. A plain read of a ref, @r, is not checked for conflicts; (ensure r) reads the ref r and puts it under the same check as a ref that the transaction writes. Two transactions that each read both balances without ensure and each change a different one can then both commit, since neither writes or ensures a ref that the other writes; the result is one that no running of the two one after the other gives. That case, write skew, is session 9's; ensure on the ref that a transaction reads and does not write is Clojure's way to exclude it. The transfer here writes both refs, and the reader reads both inside one transaction, so neither meets it.
